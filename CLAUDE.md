# HFSE SIS — Claude Instructions

A Student Information System for HFSE International School, Singapore. Modules — Markbook, Attendance, Evaluation, P-Files, Records, Admissions, SIS Admin — are surfaces of one student record, not sibling apps. The module switcher moves between them; `studentNumber` is the backbone.

## Stable rules — auto-loaded (every session)

**Everything inside `.claude/rules/` is read into context automatically, every session.** That is a Claude Code behaviour, not something a file can opt out of — a `load: on-demand` line in a file's frontmatter is descriptive only and does not stop it loading. So only four files live there, deliberately:

@.claude/rules/always-do-first.md
@.claude/rules/hard-rules.md

- `.claude/rules/design-system.md` — binding design pointer; too important to risk missing (it is small, and only points at the full docs).
- `.claude/rules/key-decisions.md` — the KD index, so a "KD #N" cite resolves with no extra read.

Do not edit any of the four without explicit user approval, and **do not add new files to `.claude/rules/`** — anything put there is paid for in every session. On-demand material goes in `docs/` (below).

## Session context

✅ **A STAFF ACCOUNT CAN NOW HOLD A TEACHER VIEW AND BE GIVEN A CLASS — 2026-09-03, 8 commits `bc499e33`..`2de95876`, migration 141 APPLIED by Mr Ace and verified 5/5. Full account: KD #206.** Mr Ace: _"a role swithcer is best here"_ and _"its basically a role switch, like we have per role view right? thats basically it plain and simple. just a simple page reload then voila"_. Six `school_admin` accounts teach in AY2026 and **four are the form adviser of record**, which gates report-card publishing. **NO schema change, NO JWT change, NOT ONE of the ~34 role-dependent RLS policies touched** — teaching was always an assignment, and `is_teacher_for_*` resolves `auth.uid()` against `teacher_assignments`, never the JWT. **THE INVARIANT: `role` authorises, `activeRole` renders.** `role` still drives the proxy, `ROUTE_ACCESS`, `requireRole`, `requireCapability` and every policy; the lens drives nav, scope, labels and to-dos and is **banned from the authorization gates by identifier AND by import** (`__tests__/auth/active-role-never-authorises.test.ts`). ⚠ **The lens can only ever NARROW** — a real teacher's entitled set is exactly `['teacher']`, so nothing about a plain teacher can change, and every server teacher-gate has the shape "if `role === 'teacher'`, restrict", which a `school_admin` never enters. A lensed page can therefore be MORE restrictive than its route, never less: the failure mode is a disabled control, never a 403 on save. Pinned by a real route test, not by argument.

⚠ **Six things to carry without reading KD #206.** (1) **`resolveClassroomScope` and `loadClassroomAccess` take the role as a PARAMETER and must never read the lens themselves** — pages pass `activeRole`, API routes pass `role`. `app/api/classroom/**` decides access on SERVICE-client data, so RLS is not behind it and the call site is the whole boundary; `__tests__/auth/view-role-call-sites.test.ts` pins the count exactly in both directions. (2) **A module the view's role cannot enter has its TILE HIDDEN**, never an empty tree — `nav-visibility.ts` drops emptied groups and would fail closed to a BLANK sidebar, silently. (3) **In Teacher view ~34 oversight-only controls disappear** (registrar dashboards, "No class", "New grading sheet", Lock/Unlock, the publication panel, every SIS/Records/P-Files/Admissions entry in Cmd+K); she GAINS "My sheets" and the cover panel. The full list is `.superpowers/sdd/role-switcher/phase-3c-report.md` §3 — **that list is what Mr Ace checks.** (4) **A wrong-view page renders a recovery notice, not a 404**, and its button switches AND returns her to that page — so the switch route takes a destination and `lib/auth/in-app-path.ts` rejects schemes, protocol-relative, backslash and control-smuggled forms (18 attack strings asserted). A real teacher still gets a plain `notFound()`; that is load-bearing. (5) **`getTeacherList()` is UNTOUCHED** — the new `getAssignableStaffList()` is a sibling filtering **`ROLES` membership, NOT `role !== null`**: the staff loader falls back to `user_metadata.role`, and the parent portal is a repo we do not own, so a single upstream write of any role string would otherwise admit all ~1,000 parent accounts into `teacher_assignments`, which has no FK. (6) **The audit log's `actor_role` is REQUIRED on `logAction`** — that is the design, because the compiler is the only thing that can find all 112 sites. There is deliberately **no `actor_view` column**: recording it would mean letting API routes read the lens; the switch itself is logged as `user.view.switch` instead.

🔴 **THE REAL FIND WAS NOT THE FEATURE — THREE GUARDS WERE BLIND, AND TWO STILL ARE.** (1) `stripComments`, shared by several guard tests, treated `/**` inside a `//` line comment as a block opener: **29 files, 538 lines of real code deleted before scanning**, including the very `loadClassroomAccess(` call a guard was counting. Guards that assert ABSENCE read that as a PASS — `active-role-never-authorises` could not see `lib/auth/capabilities.ts` (199 lines → 142). Fixed with one shared scanner that also reports its terminal mode; swept into the two other false-PASS guards. ⚠ **An apostrophe in ordinary JSX prose also desyncs it** (JSX text reads as code), which is why the true count is six files and not four. ⚠ **`write-feedback-coverage.test.ts` had a CORRECT scanner all along** — the right implementation sat in a sibling file while five guards used the broken one. (2) **`link-capability-consistency.test.ts` is blind to ~a third of the app's role guards** — its reader models `role !== 'x'` chains and cannot see `ALLOWED_ROLES.has(...)` or `||`. Measured: **41 files modelled, 32 silently ignored, ~21 of them genuine allowlists.** NOT widened; it needs its own pass. (3) `isRouteAllowed` was being handed raw nav HREFS, and a path with `?query` matches no prefix — where it **default-allows**. 11 nav rows sailed through. Enforcement was never affected (`proxy.ts` passes a clean pathname). Fixing it found **five** copies of the strip-the-query rule, two inside guard tests — a guard that strips differently from the app checks a different string than the app gates on.

🔴 **TWO DEAD ENDS WERE LIVE FOR EVERY REAL TEACHER, AND FOUR ADVISERS HAD NO NAME.** Cmd+K offered `/markbook/report-cards` and `/markbook/change-requests` to teachers; both pages bounce them (`ROUTE_ACCESS` admits `teacher` on the bare `/markbook` prefix and neither page has a narrower row). Neither href is in the teacher nav tree, so the palette was the only carrier. Separately, `loadFormAdvisersBySection` built names from a teacher-only list and dropped ids it could not resolve — so the **four form classes whose adviser sits on a `school_admin` account showed NO ADVISER AT ALL** across Markbook, Attendance, Evaluation, Classroom, Records and the SIS home page, blanked teacher cells and two filter dropdowns on the grading page, and rendered those advisers as **"(unknown user)" beside a raw uuid** on their own section's Teachers tab. ⚠ **The generalising lesson: a name lookup built on a narrow list refuses nothing — it silently renders a blank.** The same shape was still live for DISABLED staff and is closed too.

⚠ **OPEN, deliberate.** (1) **NOT BROWSER-VERIFIED** — auth is where migration 114 blanked every teacher's Teachers tab until 116 repaired it; a pass as a real teaching admin on AY9999 is the one thing tests cannot substitute for, and whether losing ~34 controls at once reads as deliberate rather than broken is a judgement only Mr Ace can make. (2) The **Assignments cut of `/sis/admin/staff` still lists teachers only**, so the six are maintained from the Accounts cut or the section's Teachers tab; widening it changes an "Active teachers" stat and a hard-coded role chip. (3) **The notification bell and the sidebar badge show different numbers in Teacher view** — both correct, different questions; lensing the bell would make it disagree with its own list, because its dropdown is served by an API route. (4) `/account`'s `getThisTermStats`, `shortcutsForRole` and `VIEW_ALL_ACTIVITY_TARGET` stay on the account role — they are questions about what `/account` is for.

⚠ **PROCESS — MR ACE ASKED "did you overcomplicate this?" AND THE ANSWER WAS PARTLY YES.** The plan had ONE Phase 3; I split it into three, and 3c (hiding the ~34 controls) went past the brief on my own ruling. The deeper miss: asked early whether the switch should change **what she sees** or **what she can do**, he chose "what she sees" — and I presented that as a RISK trade without ever pricing it. It is the difference between **~1 file** (change what role the app renders with, everything downstream already reads it, and entitlement makes it narrowing-only so it is safe) and **~30 files** (permissions keep the real role while rendering reads a second one). **Price the options, not just their risks.** ⚠ Also mine: `git add components` on a 33-file commit swept in another session's uncommitted file — **a directory pathspec is a bare `git add` over that subtree.** Caught before committing by diffing the staged set against the files known to be theirs.
