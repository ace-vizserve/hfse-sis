## Attendance — daily writer + school calendar

### KD #47

Attendance is sole writer of daily attendance. Markbook/Records/Parent are read-only consumers. Audit prefix `attendance.*`. `16-attendance-module.md`.

### KD #50

School calendar has five day-types (`school_day`, `public_holiday`, `school_holiday`, `hbl`, `no_class`) per `school_calendar.day_type` (migration 019). `school_day` + `hbl` are encodable (attendance grid accepts writes). The other three reject writes (409 on `/api/attendance/daily`). `is_holiday` is legacy, derived via BEFORE trigger from `day_type`. "Important dates / special events" stay on `calendar_events` as an overlay layer, not a day-type. **Audience precedence rule** (migration 037): both tables carry `audience IN ('all','primary','secondary')`; on read, an audience-specific row overrides the matching `'all'` row for the same date when the section's level type matches. Attendance writer at `app/api/attendance/daily/route.ts` resolves the section's level via `lib/sis/levels.ts::levelTypeForAudienceLookup`; preschool sections (YS-L/J/S) fall back to `audience='all'`. Unique key on `school_calendar` widened to `(term_id, audience, date)` so primary + secondary can each hold a row for the same date. `getEncodableDatesForTerm` + `isHoliday` apply the same precedence.

### KD #55

`/attendance` route split. `/attendance` is the analytics dashboard (registrar+ only); `/attendance/sections` is the section picker (teachers land here); `/attendance/[sectionId]` remains the daily writer. Teachers visiting `/attendance` redirect to `/attendance/sections`. Sidebar isActive: exact-match `/attendance`, prefix-match `/attendance/sections`.

### KD #76

Calendar audience scope + typed event categories (migration 037). `school_calendar` and `calendar_events` both carry `audience IN ('all','primary','secondary')`; `calendar_events` also carries `category IN (term_exam | term_break | start_of_term | parents_dialogue | subject_week | school_event | pfe | ptc | other)` + `tentative bool`. KD #50's 5 day-types stay the attendance gate — new event types live on the overlay layer, NOT as new day-types (a term-exam day is still a school day with attendance taken). UI at `/sis/calendar` exposes an `?audience=all|primary|secondary` filter tab; cell click-cycle and event create write to the active filter. Audience precedence rule: an audience-specific row beats the matching `'all'` row for the same date (KD #50 documents the read-side rule). Carry-forward stays manual: `components/attendance/copy-from-prior-ay-dialog.tsx` (renamed from copy-holidays-dialog) handles both day-type overrides + events with year-shift; default `markTentative=true` flips every copied row to `tentative=true` so the registrar reviews each before locking. ### KD #130

Recompute proration when `enrollment_date` changes (Sprint 57, 2026-06-06; assumptions register A1). Extends KD #113. The late-enrollee proration (`recompute_attendance_rollup` filters `attendance_daily` to `date >= enrollment_date`) was only re-applied on attendance writes — so correcting a wrongly-prorated student's `enrollment_date` left the existing rollups stale until the next write. Now the section-students PATCH (`app/api/sections/[id]/students/[enrolmentId]/route.ts`) fires `recompute_attendance_rollup(term_id, section_student_id)` for **every term in the AY** after a **real** `enrollment_date` change (compared to the prior value — idempotent re-saves don't re-fire), via the service client, **non-fatal** (per-term `console.warn` on error; the edit already committed, never 500s), folded into the existing `enrolment.metadata.update` audit context (`recomputedAttendance` + term count). Not a discretionary override (HFSE rejected that) — proration follows `enrollment_date`, so fixing the date is the correction path; this makes it take effect. The only date-write path today is the late-enrollee transition; the change-guard also catches a future direct date editor automatically. No migration.

### KD #163

Attendance section register + export are gated on **form adviser, per section** (2026-07-30; no migration). Closes a real read exposure: `/attendance/[sectionId]` read the session only to derive write flags and performed **no assignment check at all**, and its `/summary` sibling never read the session. Both then load marks through `getDailyForSection` / `getSectionAttendanceSummary`, which use the **service client** (`lib/attendance/queries.ts` header documents this), so `attendance_daily`'s `is_adviser_for_section` RLS never applied. Two concrete consequences, both by URL typing: a **subject-teacher-only** user saw the full per-student register (the roster itself passes RLS — `section_students` is `is_teacher_for_section`, any assignment — so only the marks were forbidden), and a teacher with **zero assignments** got an empty roster but live term stat cards (average %, perfect-attendance count, present/late/absent/excused totals).

- **Both pages now resolve capability via `loadClassroomAccess` + `canReadAttendance` (KD #160) and `notFound()` otherwise.** Deliberately reuses the classroom resolver rather than adding a fourth inline `teacher_assignments` query — its adviser-beats-subject precedence is already unit-tested.
- **Per SECTION, never per person.** A form adviser normally also teaches subjects elsewhere (both unique indexes on `teacher_assignments` are partial, so the two row kinds coexist; the adviser index keys on `section_id` alone, i.e. "one adviser per section", not "one row per teacher"). So "is this user an adviser somewhere" — the correct question for _module_ visibility in `lib/sidebar/module-visibility.ts` — is the wrong question here.
- **`GET /api/attendance/[sectionId]/export` tightened** from ANY assignment to `role='form_adviser'`, matching its two sibling read routes (`/api/attendance/daily`'s `assertAdviserForSections`, `/api/attendance/student-summary`). It was the outlier, and it streams the whole term register.
- **Knock-on:** `/markbook/sections` lists any assignment (KD #160), so its row menu's "Open attendance" + "Open write-ups" cross-links became 404s for a subject teacher. `components/sections/section-row-actions.tsx` now takes a `capability` prop (per row, threaded from the page's resolved scope) and gates both on `canReadAttendance`/`canReadWriteups`; an omitted capability falls back to oversight-or-nothing so a caller that forgets it hides the items rather than dead-ending a teacher. The KD #159 nav-consistency test walks **nav items only, not row-action cross-links** — it would not have caught this.
- **The stale claim this disproves:** `lib/sidebar/module-visibility.ts`'s header asserted "That is not a data leak — RLS and the page guards hold." True for every attendance surface _except_ these two, and KD #160 repeats the claim.

### KD #171

**Form class advisers get their own Attendance dashboard** (2026-07-31; no migration). Amends KD #55, which made `/attendance` the registrar+ analytics dashboard and bounced every teacher to `/attendance/sections`. The module therefore had **no landing surface for the person who uses it every morning**.

**The redirect could not simply be lifted.** Everything on `/attendance` is school-wide and reads through the service client, so an adviser would have seen every section's attendance — precisely the exposure KD #163 closed the day before. A scoped dashboard was required, not a lifted gate.

- **Built by composition, not by retrofitting.** The registrar's six loaders (`getAttendanceKpisRange`, `buildAllRowSets`, …) are school-wide and cached per AY; threading a `sectionIds` filter through them would change cache keys that view depends on (KD #46) — a large regression surface for a new page. Every loader used here already takes a `sectionId`: `getSectionAttendanceSummary`, `getDailyForSection`, and — better than filtering the AY-wide over-quota scan — `getCompassionateUsageForSection` + `getVacationLeaveUsageForSection`.
- **Scope is `resolveClassroomScope` + `canReadAttendance`**, the same resolver KD #163 used to gate the register. **ADVISED sections only**, never every section the teacher is assigned to. A subject teacher advises nothing, gets `null`, and keeps the old redirect — they have no attendance work at all.
- **The design: a register, not a report.** "Is today marked" is binary and expires daily, so it leads; term rates are a weekly reading and sit beneath. The today strip **collapses** when everything is in — two marked classes become one sentence, not two green cards — because absence of work should look like absence rather than turn into more content. A day the calendar says takes no marks never renders as an outstanding task: it names the holiday and the next school day. Mockup approved before any JSX: `docs/superpowers/specs/2026-07-31-fca-attendance-dashboard-mockup.html`.
- **Two things the pure engine (`lib/attendance/adviser-dashboard.ts`) gets right that a naive version would not**, both pinned by tests. `attendance_daily` is append-only for corrections (Hard Rule #6), so a corrected student holds several rows for one date — `tallyToday` dedupes to the latest per student, comparing `recordedAt` **explicitly** rather than trusting the loader's newest-first ordering; counting rows would push `marked` past the roster AND count the superseded status. And `unmarkedSchoolDays` takes the calendar's own **encodable** list (`school_day` + `hbl`, KD #50/#98) rather than walking the date range, so a public holiday can never be flagged as a day that slipped; today is excluded, since an unmarked today is the job the top of the page is already asking for.
- Status codes are the stored letters **P / L / EX / A / NC**, not words; `NC` counts as marked and is shown separately. Term comes from `resolveCurrentTermId` (KD #116), never `is_current` — the trap that pinned every report card to Term 1 (KD #164).
- **Expect it to be invisible until AY2026 has form advisers.** The dashboard renders only for a `form_adviser` row in the CURRENT AY; without one the teacher hits the "advises nothing" branch and sees the old redirect, which looks identical to the feature not working.

### KD #177

**An excused absence must say why, and both marking surfaces say it the same way** (2026-08-03; migration 109). Christina asked at the 2026-07-31 training (31:07) for somewhere to type "Medical certificate submitted", and **Melissa asked for the same thing at 32:44** as the fallback once she heard the certificate itself could not be uploaded — both verbatim in `docs/training/sessions/2026-07-31-academics-feedback.md`, which is the authoritative record of who asked for what. (Credited to Melissa alone until 2026-08-04, then to Christina alone until 2026-08-05; both corrections were written from a summary rather than the transcript. Melissa's _other_ ask, at 21:53, is the teacher-visible student profile — a different item.) `attendance_daily` carried the reason CATEGORY (`mc` / `compassionate` / `vacation`) but nowhere to put the sentence. 109 adds `ex_note`, constrained to `status = 'EX'` and capped at 300 characters, so switching EX → P cannot strand an MC note on a Present.

**The rule the two surfaces disagreed about.** The daily register has always refused to submit an excused student with no reason; the term grid saved on every click and so wrote one immediately. That is a difference in plumbing, not in policy — and it showed: **2,511 of 2,516 EX rows on production carry no reason.** Excused is now a disclosure on both surfaces, not a stamp: it opens the three reasons, and whichever reason is picked saves the mark and the reason together. The note stays disabled until then, because the note saves as part of the excused mark, so offering it first invites the very row this prevents.

- **Deliberately a UI rule, not a `CHECK` constraint.** Nearly all 2,511 reasonless rows are the AY2025 paper-register backfill, where the reason was never captured. A constraint needs a decision about that history first. The measurement is the reason the decision went this way — not an assumption about it.
- **The audit trail records that a note was PRESENT, never its text.** `audit_log` is readable by every `is_registrar_or_above()` user — wider than the mark's own read scope — and its rows can never be edited or deleted, so a note typed in error would be permanent.
- **`sameMark` was the near-miss.** It compared status and reason only, so a note-only edit produced zero submit entries and the UI said "No changes to submit" — silent data loss. It now compares the note as well, treating `''` and `null` as the same. Regression-tested.
- **The xlsx term sheet is untouched on purpose.** Its layout is `[5 fixed][N dates][6 summary]`; any inserted column shifts every date column and every merge range (KD #151). `__tests__/attendance/sheet-export.test.ts` uses `flat()`/`toContain`, so it would **pass while the template was broken** — it cannot protect that boundary.

**Marking-surface vocabulary (same date, no migration).** Both surfaces are built from `ToggleGroup type="single"` + `Textarea`, not hand-rolled buttons — the mark rows and the reason rows are each "pick exactly one", which is what the primitive is for, and it brings roving tabindex so a mark row is one tab stop rather than four.

- **One place the primitive is deliberately overruled.** A single-select ToggleGroup treats a click on the selected item as deselect and reports `''`. Right for a filter chip, wrong here: there is no "no mark" a teacher can write and every save is a permanent line in the register, so an empty value is read as "clicked the mark already set" and does nothing.
- **`STATUS_TOGGLE_WASH` exists because of a silent Tailwind trap.** `toggleVariants` ships `hover:bg-muted` and `data-[state=on]:bg-accent`, and a plain `bg-*` class does not outrank a modifier-prefixed one at any order — so each paper wash is restated under both states. It must be **literal strings**: Tailwind emits no class it cannot read in the source, so `hover:${STATUS_CELL_WASH[s]}` compiles to nothing, and the element simply carries a class matching no rule. `__tests__/attendance/status-wash.test.ts` pins the two maps together and bans `${`.
- The chosen reason takes the **full EX wash** on the drawer's 25% ground — the chip you picked is the colour of the mark you made. The reasons carry a "Reason" label; the drawer carries no "Excused" heading, because the tile above already says that word.

### KD #197

**An approved absence marks the register** (2026-08-27; **no migration** — migration 125 already carried the three `register_*` columns and nothing had ever written them). Phase 3 of the parent declaration (KD #195), riding on the approval engine (KD #196). Mr Ace, on watching the Decided tab fill: _"the attendance sheet is not showing that the filed student has been excused based on the approval details."_ Until this, the whole chain ended in a status change nobody could act on — the parent read **Approved** and the teacher's register was still blank, which is the exact guessing the feature was built to stop.

**Two rules, both answered by Mr Ace rather than assumed:**

1. ⚠ **THE REASON FOLLOWS THE KIND OF FILING, NOT THE CERTIFICATE.** _"it will be either MC or vacation leave depending on the type of declaration the parent has sent."_ An absence records `EX` / `mc`; travel will record `EX` / `vacation`. 🔴 **This CORRECTS migration 125's own header**, which said `with_medical` "selects the reason recorded under the register mark: `'mc'` with a certificate, no subtype without one." That was our assumption, written before anybody was asked, and it is wrong — `with_medical` does not change the mark at all. 125 is applied, so its file stays as history and the corrected rule lives in `lib/declarations/register.ts` and here.
2. **Approval supersedes what the teacher already marked.** A day marked `A` on Monday becomes `EX` when the certificate is approved on Wednesday. Nothing is deleted — the ledger is append-only, so the teacher's original mark and the moment it changed both survive (Hard Rule #6).

⚠ **THE SCHOOL-DAY RULE NOW HAS ONE DEFINITION, AND THAT WAS THE REAL WORK.** `isNonSchoolDay` was a **closure inside the daily PATCH handler** — unexported, unreachable. Phase 3 needed the same question asked of a date RANGE, and a second copy of a calendar rule is how the register and the sheet start disagreeing about what a school day is (the bill this repo paid at migration 115 and again across the seven gates in KD #193). `lib/attendance/school-days.ts` now holds the **decision** as a pure function with two fetch strategies over it: `createNonSchoolDayChecker` (per date, cached — the daily route, whose dates are an arbitrary list) and `expandSchoolDays` (one query for the window — the declaration, whose dates are contiguous). `__tests__/attendance/school-days.test.ts` pins both, including a text check that neither caller has grown its own copy back.

- ⚠ **The legacy branch is load-bearing and must not be tidied away**: a term with **zero** `school_calendar` rows blocks nothing (the pre-migration-019 world). Removing it refuses marks on every date of any term nobody has configured.
- ⚠ **"Has this term any rows" is asked of the WHOLE TERM, never of the window just read.** A range landing inside an unconfigured stretch of an otherwise-configured term would otherwise read as legacy mode and mark straight through a closure. There is a test for exactly this.
- **`term_id` is resolved PER DAY**, so a range crossing a term boundary is right for free and both rollups recompute (`writeDailyBatch` keys on `(term, student)`).

**Non-school days inside the range are SKIPPED SILENTLY, not refused** — and this is a deliberate difference from the daily route, which 409s on a blocked date. A teacher clicking a holiday has made a mistake; a date range has no mistake in it. A parent filing Friday-to-Tuesday is not making a claim about the weekend. The count actually written is stored and shown, so "5 days filed, 1 day marked" is legible rather than mysterious.

⚠ **A FAILED REGISTER WRITE NEVER UN-DOES THE APPROVAL.** The decision is already committed and two people made it; throwing would report a landed decision as an error and invite a second click that `approval_advance` would then refuse as already-decided. So the failure is caught, stored on the filing, shown to staff in the decision sheet, and repaired by script — and the response still says the approval succeeded. **Marks first, stamp second** (125:206: _"a stamp with no marks is the one failure mode that leaves no trace"_); production verification showed the mark at `10:01:19` and the stamp at `10:01:20`.

- **`ex_note` is left null.** The parent's note stays on the filing where the approver reads it in full; `ex_note` is the teacher's own field (KD #177), and stamping a parent's sentence about a child's illness across five register rows spreads it further than the absence itself.
- **`audit_log` gets a COUNT, not dates** — `register_days_written` / `register_days_skipped` / `register_write_failed` on the existing `declaration.approve` action, so no new action, no humanizer label, no allowlist entry.
- **Cache busts BOTH `attendance` and `records`** — the permanent record and the Academic Summary read these marks too, and busting one leaves the other showing an absence that has since been excused.
- **`scripts/repair-declaration-approvals.ts` gained a fourth pass**: approved absences with no `register_written_at`, covering both anything approved before this shipped and anything whose write failed. It passes `recorded_by: null` — a repair run is the school's own correction, not a person's decision, and stamping whoever ran the script puts a name on the register that never touched it.

**Travel was deliberately excluded here and its reason was already mapped**, because writing `vacation` days before anything counted them would silently spend a quota nobody was checking. ✅ **Shipped the same day in KD #199**, once the allowance was actually counted. ⚠ An earlier version of this paragraph cited the quota as **KD #76**; that is the calendar-audience decision. The vacation allowance is **KD #94**.

🔴 **Found while verifying, pre-existing and NOT this feature's: AY2026 has no Term 4 row.** AY2025 has four terms and AY2027 has four (undated); AY2026 — the live year — has T1, T2 and T3 only, and **T3 ends 2026-09-04**. After that date no term owns a day, so attendance cannot be marked at all and a declaration covering those dates expands to zero days **silently**. Same shape as the gap recorded in `project_ay2026_terms_row_gap` (only T1 existed; T2 and T3 were added, T4 never was). The dates are the school's to supply. ⚠ Mr Ace, 2026-08-27: the school does not have them yet, so this stays open — `rollupVacationLeave` now returns early on an undated term rather than throwing at it.

### KD #199

**Vacation leave is one TRIP, not one day — and approved travel marks the register** (2026-08-27; no migration). Phase 4, and it **corrects KD #94**, which counted `attendance_daily` rows tagged `vacation`. Mr Ace, asked directly whether one leave is a day or a trip: _"who does vacation 1 day bruh its one trip"_. The school's own workbook header — _"4 Vacation Leaves: 1 per term"_ — reads both ways, which is why it had to be asked rather than inferred. ⚠ **An earlier planning note asserted "one allowance = one trip" with nothing behind it**; that was our own writing quoted back as if it were the school's, and the answer only became a fact when he gave it.

**What the day count did:** a five-day family holiday read as **5 used against an allowance of 1**, on every surface that reports the quota — the student card, Insights, the drill, the adviser dashboard, and the toast in the marking grid, which fired "over quota" on the second day of a perfectly ordinary trip. The warning cried wolf on exactly the normal case.

⚠ **A TRIP IS ALREADY VISIBLE IN THE REGISTER AND NEEDS NO NEW DATA.** It is a run of vacation-marked **school** days with no ordinary school day interrupting it. Friday-to-Tuesday is Fri, Mon, Tue — one trip, because the weekend is not a school day. Two vacation days with an Absent between them are two trips, because the child came back to school. `lib/attendance/vacation-trips.ts::countVacationTrips` is the whole rule and it is three lines; **counting declarations instead was rejected** because it would miss a family who phoned the office, and because it would put a second source of truth beside the register that six screens already read.

- ⚠ **School days, not calendar days**, which is why the function takes a day list rather than doing date arithmetic. Bridging a weekend by "dates within three of each other" also bridges a Monday the child spent in class.
- **A trip crossing a term boundary counts ONLY in the term it started in** (Mr Ace's call). A holiday is one thing the family did, and spending two of their four yearly allowances on it is harsher than the policy says; a filing already carries a start date. Implemented as the `startedBeforeTerm` seed — nothing between two terms is a school day, so the day before a term IS the previous term's last one, making the check exact and one lookup. **The accepted hole:** such a trip eats school days in the later term without spending that term's allowance. Reaching it needs a family away across an entire ten-day break with missed school days on both sides; the approver is reading the dates anyway.
- ⚠ **`tallyVacationTripsByStudent` is a SIBLING of `tallyLeaveUsageByStudent`, not a flag on it.** The compassionate allowance really is 5 **days** per year — sharing one function is what let vacation inherit a day count in the first place.
- ⚠ **The counter reads audience `'all'` only, never the section's half.** A quota belongs to the STUDENT and is reported on cross-section screens holding no one level type; resolving per section would make the same child's allowance read differently depending on which page asked.
- **A mid-year transfer cannot split a holiday** — dates are unioned across the student's enrolments before grouping.
- **The labels changed with the number.** The student card said "days remaining" over a day count; it now says trips. Silently changing what a figure means is worse than the wrong figure.

**Approved travel now writes `EX` / `vacation`**, one entry in `REGISTER_WRITING_TYPES`. ⚠ **The ordering was deliberate**: travel waited until the allowance was counted in trips, because writing vacation days while a day-counter was live would have made every approved holiday instantly report itself as over quota on six screens.

⚠ **THE ALLOWANCE WARNS; IT NEVER BLOCKS** (Mr Ace: warn the approver, never block the parent). The filing shows the approver _"This would be trip 2 of 1 allowed this term"_ in amber, and that is all it does. The approval steps exist precisely so a person makes this call, and a family with a real reason for a second trip must be able to ask. `used` deliberately **excludes** the filing being decided — an unapproved trip has written no marks — so `used + 1` is what saying yes would make it.

✅ **Measured against production before shipping: the correction moves NO live figure.** AY2026 holds one student with vacation leave, a single day, which is one trip under either rule. The fix is forward-looking, which is the cheapest moment to have made it.

### KD #202

**A mark can be taken back off a day, and staff can attach the certificate the parent could not file — 2026-08-31, migration 134 APPLIED.**

**THE UNDO GAP WAS IN THE VOCABULARY, NOT THE UI.** Mr Ace: _"i cant undo my attendance encoding like i cant bring it back to empty wide grid and daily view"_. `attendance_daily.status` was `not null` with a CHECK of `('P','L','EX','A','NC')`, so no value meant "not marked" — the term-sheet popover offered only the five marks, and the Daily view was worse than a missing button: `computeSubmitEntries` defaults an untouched student to `'P'`, so clearing a student there did not blank the day, it wrote **Present**.

**Migration 134 makes `status` NULLABLE and NULL means unmarked.** A sixth status value was rejected: `school_days` is `count(*) filter (where status <> 'NC')`, which a sentinel satisfies, so a cleared day would keep counting as a school day with nothing against it and quietly drag `attendance_pct` down. NULL cannot — FILTER counts only TRUE and `NULL <> 'NC'` is NULL — so a cleared row drops out of every aggregate and **`recompute_attendance_rollup` needed no change at all**. It also matches Hard Rule #6's shape for grades (deletion is a null plus an audit row, never a DELETE), and the client already modelled an empty cell as `AttendanceStatus | null`. ⚠ **`recompute_attendance_rollup` was deliberately NOT re-emitted** — its body is 068's but its grants are 103's (service_role only), and copying 068 verbatim would carry its trailing `grant execute … to authenticated` and undo that lockdown, the same class of regression migration 114 caused.

⚠ **THE DAILY VIEW IS A TRI-STATE AND COLLAPSING IT WRITES WRONG MARKS.** (a) untouched → still submits `'P'`, the mark-the-exceptions convention, **unchanged**; (b) marked; (c) explicitly cleared → submits `null`. Clearing a student with no mark on file is a **no-op**, checked before `sameMark`. `tally` gained a separate `cleared` bucket — folding it into `unmarked` would have counted a blanked student as present, because the submit bar adds unmarked to P.

⚠ **WIDENING `DailyEntryRow.status` FOUND FIVE READERS THAT ASSUMED A MARK ALWAYS EXISTS**, and the adviser dashboard was the worst: `tallyToday` counted a cleared row as _marked_ while bucketing it into none of the five, so a class could read "done for today" with nobody's attendance recorded, and `unmarkedSchoolDays` keys on the date alone, so a past day whose marks were all cleared **dropped off the slipped list** and nothing would ever mention it again. `isMarked()` is the one predicate they all filter through. ⚠ The monthly-breakdown `NaN` this was first blamed on is **nearly harmless** — `obj[null]` writes a junk `'null'` property and never touches P/L/EX/A/NC; the real defect there was a month whose marks were all cleared still rendering **"20 school days · 0 present · 0%"**.

✅ **A whole-class Submit can no longer write Present over a day an approved filing covers.** An approved filing does NOT guarantee a mark exists — `lib/declarations/register.ts` leaves the filing approved and only stamps `register_write_error` when the write throws (KD #197), and its `if (days.length > 0)` guard writes nothing when the range expands to zero school days while still reporting success. ⚠ **Only the SILENT default is withheld**; a teacher who deliberately picks a mark on such a row is still obeyed, and the Term sheet's confirm has no clean equivalent in a one-action whole-class submit. **That half is open.**

**THE CERTIFICATE UPLOAD (Mr Ace: _"the simplest way is just allow the SIS users to upload the MC"_).** One control, in both marking surfaces, built once. It never asks whether a parent already filed — the person has no way to know and the server does: `POST /api/declarations/staff` creates an approved filing when there is none and attaches to the existing one when there is. ⚠ **This reverses a "do not rebuild" note that was correct when written** — a previous session invented the "parent obtains the certificate after approval" story and Mr Ace killed it; **he asked for it directly on 2026-08-31**, which is what makes it real. ⚠ **It does NOT enter the approval ladder and does NOT write the register** — the ladder vets a claim a _parent_ makes, and the teacher's own mark is the register write; so these rows carry `requestId: null` / `approvedBy: null` and a `?req=` deep link would be dead. ⚠ **It produces no queue row and no Activity event** (both derive from `approval_request_stages`), so `audit_log` is the only record — presence only, **never the path or the URL** (migration 109's rule, restated by 125).

**Replacing a certificate is TWO requests, not one overwriting call** (Mr Ace: _"reuploading in SIS will override it but theres a warning"_). The first arrives without `replaceExisting`, is refused 409 with `certificateAlreadyOnFile`, and the screen turns that refusal into the warning; only the request sent after a person agreed carries the flag. A single overwriting call would make the warning decorative — anything skipping the UI, or any retry, would replace a child's certificate with nobody asked. ⚠ **The guard is INVERTED, not dropped**: a first attach asserts there is no proof, a replacement asserts there still IS some, both in the WHERE clause. ⚠ **The replaced file is NOT deleted from storage** — losing a child's medical certificate because somebody replaced it is worse than an orphaned object — and **two staff replacing at once both win their warning, later write stands**. The audit line distinguishes all three cases in words.

⚠ **`ex_note` AND `parent_note` ARE DIFFERENT FACTS AND BOTH NOW SHOW.** The filing card used to replace the note field; Mr Ace: _"show the note regardless its internal notes"_. `ex_note` is the school's own record and never leaves the school (109 keeps it out of `audit_log`, no parent route returns it); `parent_note` is the parent's message coming in.

⚠ **"NO CLASS" LEFT THE PICKER** (Mr Ace: _"there is no NC type of attendance mark"_) — a day the class did not meet belongs to the school calendar, not a student's row. **Existing NC rows still render**, and the server's registrar-only NC guard is untouched: the API is reachable without the component, so the guard is what enforces the rule.
