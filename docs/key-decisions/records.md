### KD #67

Atomic mid-year section transfer. Reassigning an enrolled student to a new section within the same level happens through the dedicated `POST /api/sis/students/[enroleeNumber]/transfer-section` route, NOT the existing class-stage PATCH. Helper `lib/sis/section-transfer.ts::transferStudentSection` runs an atomic withdraw-old-row + insert-new-row pair against `section_students` (per Hard Rule #6: append-only) plus an admissions-side `classSection`/`classLevel`/`classStatus='Finished'` update on the same call. The class-stage PATCH rejects post-Enrolled `classSection` mutations with a 422 pointing to the new endpoint — closes the silent dual-section bug where the per-row sync's narrow scope left the student active in BOTH sections. Pre-flight rejections: cross-level transfer (same-level only), target at 50-cap (Hard Rule #5), same-section, missing studentNumber. Term-of-transfer captured in audit context via shared `lib/sis/terms.ts::getTermForDate`. UI: per-row "Move" action on the SIS Admin section roster table at `/sis/sections/[id]`. Records detail page renders a "Section transfers" history card from `lib/sis/section-history.ts` (audit-log-derived, cross-AY).

### KD #85

**SUPERSEDED (Sprint 57, 2026-06-06) — feature removed.** HFSE validation (Joann, via the assumptions register) confirmed section **index numbers are permanent and never change**; this re-number feature mutated `section_students.index_number`, contradicting that rule, so the `<RealphabetizeRosterButton>` + `POST /api/sections/[id]/realphabetize` route were **deleted**.

**Reinstated as a deliberate registrar tool (Sprint 58, 2026-06-08) — see KD #136.** The _continuous/always-on_ re-alphabetize is still wrong, but a **registrar-triggered "Generate class index"** button (numbers active rows A→Z, withdrawn retired/never reused, late enrollees appended) is the sanctioned exception — HFSE numbers classes alphabetically at year start (Joann), then freezes. The "never mutate index_number" half of this KD is narrowed accordingly. The migration-042 RPC is left **dormant** (no caller; the negative-index-staging pattern below is still a valid reference) and the `section.realphabetize` AuditAction + humanizer label are kept for historical audit rows (KD #96 dormant-object pattern). Viewing a roster alphabetically stays available via the roster table's **column sort** (a view, never a mutation). Original design below, kept for history.

Section roster re-alphabetize via Postgres RPC (Sprint 37, migration 042). New `realphabetize_section_index_numbers(p_section_id uuid)` re-assigns `section_students.index_number` 1..N alphabetically by `(last_name, first_name, middle_name)`. Active + late-enrollee rows come first; withdrawn rows append at the bottom in the same order. **Two-phase update via negative-index staging** — the `unique (section_id, index_number)` constraint is non-deferrable so a naive `UPDATE SET index_number = N WHERE id = X` loop hits violations on the first iteration; the RPC instead flips every row to its negative value (still unique, no conflicts) then assigns positives via `row_number() OVER (...)` in a CTE-driven UPDATE. Returns `{ rows_renumbered, before, after }` JSONB so the audit log captures the full rename map. Surfaces via `<RealphabetizeRosterButton>` on `/sis/sections/[id]` (registrar + school_admin + superadmin); confirm dialog explains that grades/attendance/evaluations are NOT affected (they reference section_students by UUID, not by index_number). Audit-logged as `section.realphabetize`; invalidates all operational drill caches for the AY post-update. **Pattern reusable**: any future mutation surface that needs to safely permute a column under a non-deferrable unique constraint should reuse this negative-index staging — don't reach for `DEFERRABLE INITIALLY DEFERRED` retrospectively, and don't try a JS-loop sequential UPDATE.

### KD #117

Position-aware late-enrollee joining-term decision (Sprint 50). Supersedes the `detectMidTermEnrolment` heuristic, which excluded T1 ("on-time by definition") and went silent during term breaks because `getTermForDate` returned null. New pure resolver `lib/sis/enrolment-position.ts::resolveEnrolmentPosition(terms, today)` → `EnrolmentPosition` { `activeTerm` (window contains today), `nextTerm` (earliest starting after today), `joiningTerm` = activeTerm ?? nextTerm, `isLateEnrollee` (= activeTerm != null), `canDeferToNext`, `daysLeftInActiveTerm` }. **Late = a term was in session on the enrollment date** — works for every term including mid-T1, and treats break / before-T1 / after-T4 as _not_ late. `lib/sis/terms.ts::getEnrolmentPosition(ayCode)` wraps it for today (today-term route + re-enrolment use it). **Registrar-controlled**: the system states the objective fact and suggests; the registrar decides. When `activeTerm` exists, the edit surfaces show a non-blocking prompt — "Enrolled after {activeTerm} started — late enrollee. ● Join {activeTerm} now / ○ Start in {nextTerm} instead / [Not late]"; the "Start next" option only appears when `nextTerm` exists, and a near-end warning fires when `daysLeftInActiveTerm` < ~14. **`enrollment_date` is derived from the chosen joining term** (Join now → active-term context; Start next → next term's start) so the KD #68 term-detection downstream resolves correctly. Wired into three editors — `components/sis/enrolment-edit-sheet.tsx`, `components/markbook/enrolment-edit-sheet.tsx`, `components/sis/edit-stage-dialog.tsx` — and reachable from Records (`section-roster-table` → student page) with plain-English copy. Spec + plan: `docs/superpowers/{specs,plans}/2026-06-01-late-enrollee-detection*`. Extends KD #68 (term detection) + KD #111 (`late_enrollee_term_number` override). No migration.

**Refinement (2026-06-03) — "late" = the school year has started, not "a term is in session" (user rule).** The original "_a term was in session_" definition treated a re-enrolment/enrolment during a **between-terms break** as _not_ late, so the joining-term suggestion was suppressed (gated on `activeTerm`) and the placement badge fell back to "between terms". Per the registrar's rule, **once T1 has started, anyone joining is a late enrollee — new or re-enrolled, in Admissions or Records — regardless of which term they land in.** The smart suggestion only picks _which_ term they officially join; the late tag is set either way. Only enrolling **before T1 begins** is on-time. **Resolver change:** `EnrolmentPosition` gains `yearStarted` (`min(term.startDate) <= today`); `isLateEnrollee` redefined from `activeTerm != null` to **`yearStarted && joiningTerm != null`**. `canDeferToNext` unchanged (`activeTerm != null && nextTerm != null`) — the current-vs-next choice only exists mid-term; in a break the only option is the next term (still a late join). The two server consumers (`stage/[stageKey]` + `sections/[id]/students/[enrolmentId]`) AND-it with `activeTerm` historically; both were widened to `pos.joiningTerm` so the mid-term prompt also fires between terms. **UI:** all three editors now fetch position on any re-enrol (not only when status is manually set to `late_enrollee`), render the suggestion on `isLateEnrollee` (so it shows during breaks), and present a single "Join T{next}" option when no term is active; selecting a term sets `status='late_enrollee'` + the term. The `[Not late]` escape hatch is dropped once `yearStarted` — they're definitionally late. `enrollment_date` is still derived from the chosen joining term (next-term start during a break), so the placement badge resolves to "· T{n}" instead of "between terms". Unit test (`__tests__/sis/enrolment-position.test.ts`) updated — the break-after-T1 case now asserts `isLateEnrollee: true`. No migration.

Widening it to spread a whole row — a natural refactor — would null every house on the next nightly cron, with no error and no audit entry; nobody would notice until a teacher asked why the column had emptied. `__tests__/sis/students-sync-preserves-attributes.test.ts` asserts the write stays field-scoped and bans a spread outright.
- **Writes go through one route** modelled on `vl-allowance`, gated on `ENROLMENT_PLACEMENT_WRITERS` — house is placement-shaped, and admissions should not be setting it. Audited **by name, not by uuid**, so the log reads in English.
- **Surfaces:** the permanent-record hero chip + setter, the Records students list (column **and** facet, so it can be filtered), the CSV, and the Classroom roster. The chip always renders the house NAME beside its swatch and renders **nothing at all** when unassigned — a student without a house is a normal state, and an empty chip reads as a bug. Colour cannot be the only carrier: these four colours mean nothing except "which house" (design-system §9.3).
- **Accepted gap:** the "Full application record" export presets read raw admissions columns only and can never include house (KD #162 already warns these are not a superset of the screen).
- **No houses CRUD page.** KD #153 built exactly that for grade levels and migration 086 deleted the whole thing unused. Four seeded rows, renamed once Chandana confirms the real names and colours.
- **House _points_ is deliberately not built.** Nobody has defined what earns a point, who records it, whether it resets each year, or whether there is a running leaderboard — the ledger's shape follows those answers. It also overlaps the Awards ask, which Chandana explicitly linked, so building it now risks building it twice.
