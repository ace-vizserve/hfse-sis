### KD #59

Drill loaders + dashboards + lifecycle widget read from the SIS-side column. Seeder must write both. See `14-modules-overview.md` Cross-module data contract.

### KD #70

Admissions chase scope split. Documents in two distinct workflows that share statuses but differ semantically: **chase** (parent owes us something) = `'To follow'` + `'Rejected'` + `'Expired'`; **awaiting validation** (we owe a review) = `'Uploaded'`. Admissions PriorityPanel ranks by chase-only signals so headlines aren't inflated by routine pending-review items. New `expired: number` counter on `AdmissionsCompleteness` + `'expired'` member of `AdmissionsChaseStatusFilter` + `?status=expired` sidebar quicklink. Sidebar's "Document validation" entry split per module — admissions → `/admissions?status=uploaded` (un-enrolled validation queue), P-Files → `/p-files?status=expired` (enrolled renewal queue). Phase-1 shared infra: notify/promise/bulk-notify routes accept `module: 'p-files' | 'admissions'`; email template accepts `kind: 'renewal' | 'initial-chase'`; `getDocumentChaseQueueCounts(ayCode, module)` per-module bucket gating. P-Files's chase-strip + dashboard prune (KD #71) is the symmetric subtractive half.

**Audit prefix discipline:** Admissions-originated audit events (chase reminders, bulk notify, promise marks) use the `admissions.*` prefix (`admissions.reminder.sent`, `admissions.reminder.bulk`, `admissions.mark.promised`). Admissions-team-edited rows on `ay{YY}_*` tables use the `sis.*` prefix (per KD #42 — the internal identifier stays `sis.*` even though the user-facing module is `/admissions`; e.g. `sis.profile.update`, `sis.family.update`, `sis.stage.update`, `sis.stp.update`, `sis.document.approve`, `sis.document.reject`). The `/admissions/audit-log` page explicitly lists both prefix families in its `.in('action', [...])` filter — do not use a wildcard `.like('sis.%')` which would include Records-side actions.

### KD #97

> **Amended by KD #147 (module-ownership rule).** The "Records is **read-only** on these axes" stance below is now **narrowed to the application-history axis only**. The **shared Student Profile** (Profile + Family on `ay{YY}_enrolment_applications` — identity/contacts/parents) is **editable from Records too** (it's one record; both modules write the same row). Status + documents stay owned post-enrolment by Records / P-Files respectively (Admissions is frozen on them once Enrolled). See `docs/context/22-module-ownership-truth-model.md`.

**Admissions detail is the cross-stage editor for pre-enrolment.** The `/admissions/applications/[enroleeNumber]` surface mounts every editor that operates on `ay{YY}_enrolment_*` tables: Profile, Family, Documents (view-only record for enrolled applicants — renewals live in P-Files), STP application + residence history, class-stage Enrollment editor, Lifecycle. Records (`/records/students/[studentNumber]`) is **read-only on these axes** and only ever shows the consolidated cross-year history (KD #51).

**Rule:** when a field lives on an `ay{YY}_*` admissions table, the editor goes on the admissions detail surface; when it lives on `public.section_students` (post-enrolment operational data), the editor goes on Records (per the Records pencil + transfer + re-enrol pattern). Withdrawn-then-re-enrolled students: their enrolment lifecycle edits (section assignment, enrollment status) stay on Records since those live in `section_students`; their admissions identity (profile, family, documents, STP) stays editable on `/admissions/applications/[enroleeNumber]` for the AY they enrolled in.

**Why not on Records:** moving the admissions-table editors to Records would sever the admissions team from their operational surface mid-funnel. Admissions retains these editors through enrolment; once Enrolled, the Documents tab adds a cross-link banner directing renewal + chase work to P-Files, but the view-only record stays available for audit purposes.

### KD #118

Early-bird application window — SIS Admin owns it, Admissions reads it (Sprint 51, 2026-06-02). Extends KD #77; restores the KD #48 boundary (SIS Admin defines config, operational modules consume). **Model:** two orthogonal booleans on `academic_years` — `is_current` (exactly one) and `accepting_applications` (window open). **Rule: an AY accepts applications iff it is the active year OR it is the single upcoming year opened for early-bird.** No schema change.

- **Single-select engine** (`lib/sis/early-bird.ts::computeEarlyBirdClosures`, pure + unit-tested): opening a non-current AY closes every _other_ non-current AY currently accepting, so at most one upcoming AY is ever open. Enforced server-side in `PATCH /api/sis/ay-setup/accepting-applications` (gate `school_admin`+`superadmin`); the current AY is never in the single-select pool (plain flip).
- **Rollover** (`PATCH /api/sis/ay-setup` switch-active): on activation, the new current AY's window is auto-opened (`accepting_applications=true`) and the outgoing AY's is closed (`=false`). The close is a correctness requirement — a retired year left accepting would satisfy `accepting=true AND is_current=false` and be mistaken for the early-bird upcoming AY by `getUpcomingAcademicYear()`. Audit context gains `accepting_opened`/`accepting_closed`.
- **SIS UI:** per-row descriptive shadcn `Switch` on `/sis/ay-setup` (every row) via `components/sis/ay-accepting-applications-toggle.tsx`. AY creation no longer sets early-bird (removed from the wizard + `CreateAySchema`). The AY Readiness pill (KD #109) turns amber **"Setup needed"** when the current AY's setup is incomplete — the chosen signal for "you activated an under-configured year" (no switch-dialog warning was added).
- **Admissions is read-only:** `/admissions/upcoming/applications` shows the open early-bird AY's pipeline + a "managed in SIS Admin" indicator; the empty state points to AY Setup. No open/switch/close control. `getUpcomingAcademicYear()` is its only AY-state read.
- **Same-day history:** an intermediate Sprint 51 pass put the open/switch/close control _inside_ Admissions (`EarlyBirdAyControl` + `listSelectableAcademicYears`); both were removed when the control was relocated to SIS Admin per KD #48. The git log shows the Admissions-control commits followed by the SIS-owned relocation — the SIS-owned state is canonical.

### KD #119

### KD #140

### KD #157

Student Profile **format-validation parity** with the admissions portal + passport/pass **display masking** (2026-07-28; no migration). The shared Student Profile (the `ay{YY}_enrolment_applications` identity row, editable from BOTH Admissions and Records per KD #97/#147) validated almost nothing beyond length and blank→null — while the external admissions portal, the original point of entry for every one of these fields, enforces real format rules. Editing inside the SIS could therefore silently reintroduce exactly the drift the system exists to remove.

- **Format rules ported verbatim from the portal** (`lib/schemas/sis.ts`): `optionalNric` `/^[STFGM]\d{7}[A-Z]$/`; `optionalPhone` `/^\+?\d+$/` (applied to `homePhone`, `contactPersonNumber`, `referrerMobile`, `{father,mother,guardian}Mobile`); `optionalPostalCode` digits-only; `optionalEmail` upgraded from a loose custom regex to zod's `.email()`. `optionalNumberOrText` stays for the non-phone numeric-ish fields.
- **Nationality is now a constrained picker, not free text.** Confirmed against the portal's own `LocationSelector` (`field.onChange(value?.name)`) that the stored value is the **country NAME** (e.g. `"Philippines"`), never the demonym or an ISO code. New `lib/data/countries.ts` exports `COUNTRY_NAMES` + `COUNTRY_NAME_SET` from the **MIT-licensed `countries-list`** package — the first pick, `country-state-city`, is **GPL-3.0** and was caught in review and swapped before merge (avoid it; copyleft in a proprietary SIS). New `components/sis/country-combobox.tsx` (Command+Popover) is the only write path; the schema refines against the same `COUNTRY_NAME_SET`, so the UI's offer-set and the schema's accept-set cannot drift.
- **Legacy values are never force-changed.** An off-list stored value renders as a selectable "`{value}` (current)" item (same idiom as the `kind: 'select'` fallback for `preferredPaymentScheme`/`Method`), and the combobox has a "Clear selection" item so nationality can still be blanked.
- **THE SUBTLE PART — validation is changed-field-only, and this is load-bearing.** Both edit sheets submit the **WHOLE form** on every save (`buildDefaults()` seeds every schema key from the current row); a naive strict schema therefore re-validates untouched legacy values and **blocks a save on a field the registrar never touched** (e.g. editing a middle name fails because the stored nationality is `"Filipino"`). Fixed with `build{Profile,Father,Mother,Guardian}UpdateSchema(changedFields)` — a gated field NOT in `changedFields` falls back to its pre-tightening loose validator. Applied on BOTH sides: the client compares against the loaded `defaults` via a custom RHF resolver; **both PATCH routes fetch the `before` row BEFORE parsing** and diff the raw body against it (one fetch, not two). Anyone touching these routes must preserve that ordering — parsing first would make the check circular. Known residual: the client's baseline is a page-load snapshot, so a concurrent edit by someone else can make the server judge a field "changed" and 400; fails safe, clears on refresh.
- **Route hardening from the same work:** because the `before` fetch now precedes zod (which is what normally strips unknown keys), both routes filter the body's keys against the schema's own `.shape` before building the PostgREST `.select()` — otherwise a stray key reaches the DB as a column name and 500s the save.
- **Masking (display-only, NOT validation):** `passportNumber`/`pass` + the 3 parent equivalents (8 fields) render masked with a per-field reveal toggle on BOTH the edit sheets (`components/sis/sensitive-input.tsx`, `kind: 'password'`) and the read-only view tabs (`Field.sensitive` on `components/sis/field-grid.tsx`, which became a client component for the per-row reveal state). Expiry dates are never masked. `SensitiveInput` sets `autoComplete="new-password"` + `data-1p-ignore`/`data-lpignore` so a password manager can't autofill a credential into a passport column, and both new components `forwardRef` + spread rest props so shadcn `FormControl`'s injected `id`/`aria-describedby`/`aria-invalid` actually reach the control.
- **Deliberately out of scope:** required-ness parity (the SIS edits existing, often-partial records — every field stays nullable) and passport/pass **number format** rules (the portal's exact regex wasn't available; only display is masked).
