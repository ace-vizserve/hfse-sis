## Markbook — core grading mechanics, sheet config, slot metadata, bulk lock

### KD #3

Teacher assignments in `teacher_assignments(user, section, subject, role)` — `form_adviser` or `subject_teacher`. Gates grading-sheets list + section comments.

### KD #4

Weights per `(subject × level × AY)` in `subject_configs`; Primary 40/40/20, Secondary 30/50/20; never hardcoded.

### KD #5

Max 5 WW + 5 PT slots per sheet; max 50 students per section.

### KD #6

Annual grade = `T1×0.20 + T2×0.20 + T3×0.20 + T4×0.40`, 2dp. `lib/compute/annual.ts`.

### KD #99

`sync_grading_sheets_from_config(p_config_id uuid)` RPC (migration 052b). Grading sheet `ww_totals/pt_totals/qa_total` columns are denormalized copies of subject_configs at sheet-creation time. When SIS Admin updates `ww_max_slots`, `pt_max_slots`, or `qa_max` on a `subject_config`, this RPC brings all **unlocked** sheets linked to that config into sync — locked sheets are never touched (Hard Rule #5). Resize behaviour: ww/pt arrays extended → new slots default to max score 10; truncated → trailing scores/totals dropped; `qa_total` replaced unconditionally with the new `qa_max`. Called by `PATCH /api/sis/admin/subjects/[configId]` immediately after the DB UPDATE, before the audit log write. Returns `jsonb` with `rows_synced` count for the audit trail.

### KD #105

WW/PT slot metadata extension — date administered + optional page# (migration 057). `grading_sheets.slot_labels` JSON shape migrated from bare strings to `{ label, date, page }` objects per WW/PT slot; QA stays a single nullable string. Migration 057 one-shot coerces existing string entries to `{ label: "...", date: null, page: null }`. `ActivityLabelsForm` / `LabelRow` gain 3-column layout (Description · Page # · Date administered) + "Use today" quick-button. `SlotChip` renders date + page conditionally, omitting missing fields; muted styling when label set but date not. `saveLabel` PATCH accepts `Partial<SlotMeta>` and merges server-side (field-level blur doesn't clobber other fields). `SlotMetaPatchSchema` in `lib/schemas/grading-sheet.ts`. Publish-readiness `GET /api/sections/[id]/publish-readiness` adds a `slot_dates` soft-warning block (KD #28): cross-references `grade_entries.ww_scores/pt_scores` arrays against `slot_labels` date fields; surfaced as amber `ChecklistRow` with `CalendarDays` icon in `components/admin/publish-window-panel.tsx`. **Update (2026-06-03):** that `slot_dates` publish-readiness soft-warning was **removed** from `GET /api/sections/[id]/publish-readiness` + `<PublishWindowPanel>` — administered dates are a score-record concern, not report-card-related (KD #75 audit).

**Update (2026-06-09) — slot label/date do NOT gate score-cell entry.** An earlier version of this KD stated "both `label` AND `date` must be set to unlock score cells." This gate does not exist in the code. Verified: `components/grading/score-entry-grid.tsx` line 538 — `const inputsDisabled = r.withdrawn || r.is_na || readOnly` — the only conditions that disable a `<ScoreInput>` cell are: row is withdrawn, row has `is_na` set, or the sheet is `readOnly` (locked). Slot `label`/`date`/`page` are **optional metadata** rendered in the column-header chip and on the score record; they are recommended for completeness but **do not gate score entry**. The per-cell unlock logic is unchanged from the original WW/PT/QA implementation. The prior Update (2026-06-03) line "The label-AND-date cell-unlock gate described above is unchanged" was also incorrect and is superseded by this note.

**Update (2026-06-09, pt 2) — soft "unlabeled scored slot" flag + "Ongoing" date value.** HFSE confirmed **subject teachers own both the activity labels AND the scores** (same person → no cross-role bottleneck). Decision: still **NOT a hard gate** on scoring (labels aren't report-card-rendered; hard-blocking the core action for a record-quality nicety is disproportionate; no observed evidence labels go missing) — instead a **soft signal**: a WW/PT slot with ≥1 score but **no description** is flagged in the `ScoringGuide` (`components/grading/score-entry-grid.tsx`) — the `ActivityRow` shows an amber `AlertTriangle` "Needs a label" (was muted "No label set"), and the collapsed summary appends "· N need a label". "Has a score" is computed over the **full roster** (`rows`, not `visibleRows`) so the flag doesn't flicker under filtering. Scoring is never blocked. **"Ongoing" date-administered value:** HFSE's workbook uses both real dates AND the literal "Ongoing" for the date administered, so `SlotMetaSchema.date` now accepts `'Ongoing'` OR `YYYY-MM-DD` (`lib/schemas/grading-sheet.ts`); the labels PATCH route's inline `sanitizeDate` (`app/api/grading-sheets/[id]/labels/route.ts` — note: the route sanitizes inline, it does NOT parse via `SlotMetaPatchSchema`) passes `'Ongoing'` through; the editor (`activity-labels-dialog.tsx`) gained a reusable `DateAdministeredField` (DatePicker + an "Ongoing" toggle ↔ amber pill + clear); the read-only chips already render "Ongoing" (the `formatChipDate` regex no-matches → returns the raw string). UAT note: the academics alignment doc A-06 (which says labels are optional) stays correct — labels remain optional, just now softly flagged when a scored slot lacks one.

**Update (2026-07-24) — the soft-only decision above is REVERSED. A hard gate now exists, scoped to a slot's first score only.** Mr Ace revisited this with a new, concrete motivation the earlier decisions didn't have: HFSE's teacher-owned SOW _feature_ was built once and then fully removed (KD #108/#110 — too much upkeep, drifted from what teachers actually taught), so there's no live curriculum-plan record left in the system; the per-slot description is now the closest thing to letting a coordinator sanity-check "what was actually taught, and roughly when" against pacing. Before shipping, a live-data check found 1,662 existing scored-but-unlabeled `(sheet, slot)` pairs (mostly in the historical AY2025, only 29 in the live AY2026) — driving the specific shape of the reversal below, so the fix doesn't retroactively punish that backlog.

**What actually gates now:** a WW/PT/QA slot's very first score (roster-wide — the first time ANY student gets a score there) is intercepted by a dialog requiring Description + Date administered (WW/PT) or Description only (QA) before the score is accepted. **A slot that already has ≥1 real score — from before this shipped, or from any student since — is permanently grandfathered, gate-exempt, no backfill.** Editing an already-scored slot never gates, only a slot's genuine first entry does. Page # still never gates. `'Ongoing'` still counts as a satisfied date.

**Enforced in two places, not just the UI** (closing the exact gap the 2026-06-09 note above was correct about at the time): the shared predicate `slotMetaSatisfied`/`slotRosterScored` (`lib/grading/first-score-gate.ts`) is imported by BOTH the client (`components/grading/score-entry-grid.tsx` — `commitScore` intercepts the three `ScoreInput onCommit` sites and opens `components/grading/first-score-label-dialog.tsx`) AND the server (`app/api/grading-sheets/[id]/entries/[entryId]/route.ts` — an `if (!sheet.is_locked)` block rejects a genuine first score with `422 label_required` unless the same request also supplies a `slot_label` to satisfy it). **Gate applies only to the unlocked, direct-entry path** — the locked-sheet change-request (Path A) and correction (Path B) flows (Hard Rule #5) are untouched by design, proven by test (a call-count spy on the gate's own roster query, not just code inspection) to never fire on either. One combined write: the label merges into `slot_labels` (via `lib/grading/slot-label-sanitize.ts::mergeSlotLabel`, sharing the same sanitize rules — `'Ongoing'`/ISO/trim/cap — the labels route uses) BEFORE the score write, in the same request, not two separate PATCHes. No schema/migration change — reuses the existing `slot_labels` jsonb column as-is.

The client-side check deliberately reads `savedRowsRef` (server-confirmed roster state), never the file's pre-existing `wwScored`/`ptScored` — those are memoized on `rows`, which updates optimistically on every keystroke, so by commit time they'd already read the just-typed slot as "scored" and the gate would never fire.

Migration `057_grading_sheet_slot_meta.sql`'s header comment ("A slot unlocks for score entry only when BOTH label AND date are set") predates all of this — it was written aspirationally, never actually implemented, and the 2026-06-09 note above correctly caught that gap. It's now roughly true again, minus the first-score-only/grandfather nuance it doesn't describe. Spec: `docs/superpowers/plans/2026-07-24-first-score-label-gate.md`.

**Update (2026-07-24, pt 2) — Activity labels panel is a drawer, not an always-expanding inline block.** `ScoringGuide` (`components/grading/score-entry-grid.tsx`) previously expanded in place above the score grid — with all 10 WW/PT slots + QA rendered as full editors, it ate ~400px of scroll before the roster even started, regardless of class size. The panel's toggle row is now a fixed-height trigger strip (same eyebrow/summary/amber-flag content) that opens a `Sheet` (`sm:max-w-xl md:max-w-2xl`, wider than the shadcn default so the Description/Page/Date row has room) containing the identical grouped Written Works / Performance Tasks / Quarterly Assessment `ActivityRow` editors — same autosave-on-blur, same soft "needs a label" flag. No change to save/commit behaviour, only where the editors render. Alongside this, `DateAdministeredField` (used here and by `FirstScoreLabelDialog`) was simplified from two floating buttons (a full-width `DatePicker` fighting a text "Ongoing" button for space — the original cramping culprit) to a `DatePicker` + a plain **"Ongoing" checkbox**: checking it sets the value to `'Ongoing'` and disables the date picker (discarding its value, same as the old "clear and switch" behaviour); unchecking clears back to empty. No schema/API change — same `'' | 'Ongoing' | 'YYYY-MM-DD'` value contract.

### KD #131

Bulk manual grading-sheet lock (Sprint 57, 2026-06-06; assumptions register M5). HFSE confirmed grading sheets have due dates → keep **both** auto-lock-by-date (cron `lock-overdue`) **and** manual locking; the gap was bulk. New **`POST /api/grading-sheets/bulk-lock`** (`{ ids: string[] }`, cap 200) mirrors the single-sheet lock route exactly — same `requireRole(['registrar','school_admin','superadmin'])`, locks only the **unlocked** ids (already-locked skipped, not errored), one `sheet.lock` audit row per newly-locked sheet, `invalidateDrillTags('markbook', ay)` once; returns `{ locked, skipped }`. UI: a select column + **"Lock selected"** bulk-action-footer button on the grading list (`grading-data-table.tsx`, registrar+ only, unlocked rows only, `AlertDialog` confirm noting post-lock edits need the change-request flow). The unified `<DataTable>` shell (KD #84) gained optional `SelectionConfig.enableRowSelection(row)` (per-row gate) + `selectionResetSignal` (clears the footer after the action) — additive, existing consumers unaffected. Hard Rule #5 preserved (locking needs no approval — it ENABLES the post-lock change-request flow). No migration.

**Update (2026-09-29) — an EMPTY grading sheet can be removed; one with anything entered cannot.** Mr Ace: _"theres no way to un-attach a grading sheet to a section"_ (case: P1 Obedience carried Christian Living T1–T3 sheets, 18 blank rows each, for a subject not on the class's list). **`DELETE /api/grading-sheets/[id]`**, same audience as creating one (coordinator, school admin, superadmin). The rule is `lib/grading/sheet-removal.ts`: refused (409, plain English) when the sheet is **locked**, when **any row holds anything** — a WW/PT slot value (a 0 counts, Hard Rule #3), exam score, any derived PS/initial/quarterly, a letter, an excused slot — or when it has **any history**: a `grade_audit_log` row, an `audit_log` row against one of its entries, or a change request. Otherwise the still-blank rows are deleted, then the sheet (FKs are RESTRICT, so a score typed in the same second makes the sheet delete fail and the sheet stays), with one `sheet.delete` audit row snapshotting class, subject, term, AY and row count. Hard Rule #6 holds — no entry with a value is ever deleted. UI: **Remove sheet** in the subject-setup term drawer's expanded row (inline confirm, never a dialog on the drawer; disabled with the reason when refused — `section-terms` returns `removable` + `removeBlockedReason` per term) and on `/markbook/grading/[id]` for the same roles, only when removable (small confirm, then back to the list). ⚠ `is_na` alone does NOT count as entered (same-day fix): sheet creation seeds it TRUE for every late enrollee, which made those sheets unremovable forever; a person setting N/A leaves history (`audit_log` before lock, `grade_audit_log` after), which the history check refuses. Excused slots are never set automatically (default `'{}'`, only the audited registrar route writes them), so they still count. No migration.

### KD #176

**A subject config's slot/score numbers are a CEILING, not a broadcast value** (2026-08-01; migrations 107 + 108). Two defects in `sync_grading_sheets_from_config`, both found while triaging the 2026-07-31 academics training.

**1. It resized denominators and never recomputed the grades.** The RPC propagates `ww_max_slots`/`pt_max_slots`/`qa_max` to every unlocked sheet for a config — all four terms, every section, every level — and resizes the matching `grade_entries` arrays. It did **not** touch `ww_ps`/`pt_ps`/`qa_ps`/`initial_grade`/`quarterly_grade`, and being a SQL function it cannot: `lib/compute/quarterly.ts` is the only place the formula lives (Hard Rule #2) and a second copy of the transmutation table in PL/pgSQL is not acceptable. The stored `quarterly_grade` is what the report card **prints** (`build-report-card.ts` reads it directly), so this produced wrong printed grades that stayed wrong until someone happened to re-save a score on that sheet.

Fixed by moving the recompute into TypeScript (`lib/grading/recompute-sheet.ts`, extracted from the per-sheet totals route, which was the only correct implementation and is now the shared one). Migration 107 makes the RPC return `sheet_ids`; the caller recomputes exactly those. **Reading the ids back from the RPC rather than re-querying closes a real race** — a sheet locked between the two would be resized and then filtered out of the recompute, leaving a stale LOCKED sheet, which is the worst case since those feed published cards. The caller prefers `sheet_ids` and falls back to its own query, so it is correct in either deploy order. Sheets are re-read at recompute time and any now-locked one is skipped and reported (Hard Rule #5 — a background recompute must never be a post-lock edit). The sync stopped being best-effort: failure now returns 500 with a pointer to the new `POST /api/sis/admin/subjects/[configId]/resync`, which exists because `subjectConfigUnchanged` short-circuits a re-save of identical values — after a partial failure the operator's instinct (press Save again) returns success while doing nothing.

**Measured before fixing.** `scripts/audit-grade-recompute-drift.ts` (read-only, `--ay`, `--all`, exits non-zero on drift) found the config-sync bug had **not** bitten production — all unlocked AY2026 sheets were clean. One locked sheet did drift (SCI · Discipline 1 · T2, 29 students), from the **grading backfill import**, not this RPC. Critically the fix direction was the opposite of the obvious one: all five stored values reproduced exactly under the _sibling_ sheets' totals, so the **grades were right and the totals were wrong**; recomputing would have pushed 29 real students down. Repaired via `scripts/backfill/gen-ay2026-sci-discipline1-t2-totals-correction.ts`, which refuses to emit SQL unless that reproduction still holds. **The audit tool must skip non-examinable subjects** — their `quarterly_grade` is a band-representative integer (95/87/82/70) standing in for a letter, not a formula output; comparing them produced ~700 false positives on AY2025 and one wrong diagnosis before it was caught.

**2. It broadcast values over deliberate per-section settings.** `qa_total = v_qa_max` was written unconditionally to every unlocked sheet on **every** save, including saves that only touched a slot count. HFSE agrees a Scheme of Work before each AY and that broadcast is the intended workflow (Chandana, 2026-07-31) — but mid-year changes happen, "rare but not impossible", and there the broadcast reverts a per-section exam total (a Secondary paper out of 140 while the level sits at 100) silently, with the teacher who set it never told.

Two rules, both **no-ops at the start of an AY** so the SOW workflow keeps zero friction: (a) `findTruncationBlockers` refuses a slot reduction that would erase entered marks — 409 naming components and 1-based slot numbers, a `0` counting as a real mark per Hard Rule #3, because a score cannot be recovered _from_ an audit row so blocking beats logging; (b) `resolveQaTotal` only overwrites a sheet still holding the **old** `qa_max` — a customised sheet is left alone. Migration 108 stops the RPC writing `qa_total` entirely: **SQL owns array shape, TypeScript owns values.** The caller snapshots each sheet's prior `qa_total` _before_ the RPC, so it is correct in either deploy order.

**Do not "fix" this by adding per-subject WW/PT default max scores.** Measured against prod: max scores follow a **level ladder** (AY2025 English — WW `[10,10,10]` at P1–P2, `[15,15,15]` at P3–P4, `[20,20,20]` at P5–P6 and Secondary; PT `[30,30,25]` across Secondary), with sections inside a level still differing. A single per-subject default is wrong at nine levels in ten and would recreate the `qa_max` problem these rules exist to contain.

**Resolved 2026-08-01 — the sheet is the right place, and SIS Admin keeps only the weights and the ceiling.** Per-subject × level configs were considered and rejected too: the sheet's Totals editor already sets max scores, the exam total and any slot count at or below the ceiling, so per-section configuration is a solved problem in the wrong place rather than a missing feature. Accepted cost: that editor is coordinator+ only, so a genuine mid-year SOW change means opening each affected sheet — acceptable while changes stay rare, and the trigger to revisit is a real level-wide mid-year revision, at which point the answer is **bulk totals editing**, not per-level configs. The subject form now states its blast radius ("N grading sheets across M classes will be updated. Locked sheets are not changed.") from `lib/sis/subjects/sheet-impact.ts`, and its old warning that "scores in removed slots will be lost" was corrected — that stopped being true when the truncation refusal landed. Full reasoning in `docs/sprints/development-plan.md` under the academics-training section.

### KD #179

**At-risk compares the components, not just the term grade — and slot identity is deliberately never built** (2026-08-03; no migration). Koh described a student who scored 90 in Term 1 and dropped in Term 2; asked to be precise, Hermilita added "not only for the quizzes, but also for exam, for overall". The Alerts column compared `quarterly_grade` alone, which is the one of those three that can hide the other two: written work can collapse while the exam rises to cover it, and the alert never fires.

- **`loadPriorTermGrades` now selects `ww_ps`, `pt_ps`, `qa_ps` alongside the term grade.** Same query, same joins, no extra round trip. `ALERT_METRICS` drives four comparisons and the dialog names which one moved.
- **The ±5 threshold was four separate literals** — the comparison, the chip's aria-label and three lines of dialog copy — which could silently disagree after any one edit. One exported `GRADE_ALERT_THRESHOLD` now. It stays a **code constant**, following `AT_RISK_ATTENDANCE_THRESHOLD_PCT`: a display heuristic for drawing a teacher's eye, not a policy HFSE has adopted. Move it to `school_config` the day they tell us what the number should be — a tunable knob nobody has an opinion about is just another empty admin field.
- **The mid-term half: `outlierSlots`.** No cross-term comparison can answer "she bombed last week's quiz" — that happens long before a term grade exists. This flags a score at least 10 points below that student's own average across the other scored slots on the **same sheet**, normalised by each slot's own maximum, silent below three scored slots, and blind to blanks (Hard Rule #3). No query and no slot identity: every number is already on screen. It is the **only** signal that exists in Term 1.

**AMENDED 2026-08-03, same day.** Two things shipped here were wrong and are now removed.

- **The Alerts column is gone**, and with it the amber tint on flagged score cells. Re-reading the transcript rather than the summary of it settled the question: Koh asked the system to "**flag out students**" so that "the subject teacher or the FCA got to contact the parents" — a LIST and an ACTION. A column of chips at the far right of a wide grid is neither; it answers for one student at a time, and only once you have scrolled past every score to reach it. Tinting individual score cells failed for its own reason: a thirty-row grid is already dense with numbers, so per-cell colour read as noise rather than as signal.
- **`GradeLookupDialog` replaces both**, reusing the attendance sheet's "Look up student" pattern unchanged — same words, same two-view shape, same back link, so two modules teach one habit. The count rides on the trigger, so the finding is visible without opening anything and absent when there is none. The list ranks "Needs a look" above "Everyone else", roster order within each, every row carrying enough to triage unopened. Unlike the attendance version it needs **no fetch**: every number is already in the grid, so it re-ranks as scores are typed. Steady students stay listed — it is also just a lookup.
- **The detail panel was rebuilt from its own defects**: it printed `−6.666699999999999`; it set LAST term's value in the big type and never showed the current one, so "what is her written work now" had no answer on screen; and it stamped an orange SIGNIFICANT badge on every row over the threshold, **including improvements** — a 58-point rise wore a warning. Now one decimal, both values as `88.3 → 73.3`, and direction carried by the colour of the number, which deletes the badge rather than restyling it. The **term grade sits above its three components** (Mr Ace's cut: it is the result, they are the working) with weights printed, because the weights are why a fall in two parts still produced a rise overall. One tab per earlier term replaces one card per prior term PER COMPONENT — sixteen cards by Term 4, four lines now.
- **Still unbuilt:** Koh said "the subject teacher **or the FCA**". A form class adviser has no grading sheet, so none of this reaches them. That half needs a different surface in a different module and is the larger part of what she asked for.

**Do not build same-slot-across-terms comparison.** Slots are array positions with index-positional free-text labels; the arrays resize per sheet; KD #105 records 1,662 scored-but-unlabeled pairs that are permanently grandfathered; and the labels carry page numbers — i.e. sequential curriculum, not repeated instruments. Even executed perfectly, comparing a fractions quiz to a geometry quiz is noise dressed as signal. **Components are normalised percentages and comparable; slots are not.**

### KD #211

**A grading sheet lists the ROSTER, not the grade rows** (2026-09-15, migration 156).

The page loaded its students with `from('grade_entries')`, so it could only draw a child who already had a row on that sheet. A student placed after the sheet was generated **disappeared from their own teacher's sheet**.

Everything built around that was a workaround. The page called `seed_grade_entries_for_sheet` **on every render** to manufacture blank rows — a write on a page view, measured at 71–121ms, awaited before the page's parallel fetches. Its own comment claimed it was "typically a no-op insert"; five of five sampled sheets were each missing two or three students, and **929 rows across 469 sheets** were still absent. Seeding those rows earlier (a trigger at placement) was tried first and rejected: it keeps the false requirement that a blank row must exist before a student is visible, and only moves who creates it. Mr Ace: _"its simple students should just show bruh."_

**Now:** the page reads `section_students` and attaches whatever grade row exists. `entry_id: ''` means unscored, not absent. Nothing needs a row in advance, so nothing seeds one — not on render, not at placement. The **first saved score creates the row**, via `upsert` on the `(grading_sheet_id, section_student_id)` unique constraint (migration 035), so two teachers typing the same child's first score produce one row rather than a duplicate. Migration 156 adds the matching INSERT policy; 152 had deliberately left INSERT denied on the reasoning that only the seeder created rows.

⚠ **The grid's row identity had to change with it.** It keyed React rows, `savedRowsRef` and every commit callback on `entry_id`, which worked only because every student was guaranteed a pre-created row — the very thing the render-time write existed to guarantee. Unscored students all share `''`, so rows are keyed on `section_student_id` now. **`tsc` cannot catch that** (both are `string`); the tests did, because two fixtures had been sharing one `section_student_id` all along. `StudentAlertRow.entryId` was renamed `rowId` rather than left holding something that is not an entry id.

`seed_grade_entries_for_sheet` survives as a manual repair and is still called by `create_grading_sheets_for_ay`; it is simply off the read path.

### KD #218

**A grading sheet says which components it is graded on, and at what weights** (2026-09-15, migration 159 APPLIED).

Miss Joann, registrar training: S3 Filipino has an exam in some terms and not others, and Global Perspectives had no exam in Term 3 — _"those subjects have PT scores only, and the PT score effectively is the exam"_. She asked whether she has to untick something per term. There was nothing to untick.

🔴 **The flag she was pointed at is the wrong one, and the right one did not exist.** `subjects.is_examinable` means numeric WW/PT/QA grading versus LETTER grading (migration 049 — MUSIC, ARTS, PE, HE, CL, CA, PEH, PMPD), not "has an exam". Unticking it for Filipino would turn Filipino into a letter-graded subject **in every academic year at once**: the column has no AY dimension, and migration 080 had already considered and refused a per-AY `grade_type`. Mr Ace: _"our definition of examinable is wrong … its the grading sheet that needs it instead of the subject."_

🔴 **The cost was a live defect.** `lib/compute/quarterly.ts` sums `(qa_ps ?? 0) * qa_weight` — a missing component contributes **zero, it does not give its weight back**. Filipino at 30/50/20 with no exam gave a full-marks student initial 80 → quarterly **87**; Global Perspectives on performance tasks alone gave **72**. **No test covered it**: the null-exam case was only ever exercised with every component null, which correctly returns null.

⚠ **`lib/compute/quarterly.ts` IS NOT MODIFIED, and must not be.** With `qa_weight` at 0 the term is already zero and the rest already sum to 1 — the formula was never wrong, it was being handed the wrong weights. Hard Rules #1 and #2 stand untouched.

**What migration 159 adds:** `grading_sheets.ww_weight / pt_weight / qa_weight`, `numeric(4,2)` nullable, with a CHECK that they are all null or all set and sum to exactly 1.00. **Null means inherit the subject config**, so applying it changed not one grade. This completes the pattern `qa_total` already followed (KD #176 — the config is a CEILING, not a broadcast); weights were the one grading number left at year level. One resolver, `lib/grading/resolve-sheet-weights.ts`, is sheet-or-config, **one hop, never a chain** — migration 137's report-label leak is the cautionary tale — and `__tests__/grading/sheet-weight-read-sites.test.ts` asserts no compute site reads a weight off a `subject_configs` join.

**Two scopes, deliberately.** Subject setup sets it for **(subject × term)** — every class, because twenty-odd sections is not something to click through. The grading sheet's _Edit totals & slots_ sets it for **one class**, the exception Mr Ace asked for: _"currently its per level and there might be cases where its per section"_. Both write the same three columns; the sheet editor carries it in the **same PATCH as the totals**, because both change what a grade means and both need the same recompute — two endpoints would be two recomputes and a chance to interleave.

⚠ **The fan-out must go through TypeScript.** `sync_grading_sheets_from_config` (migration 052) moves denominators in SQL and cannot recompute, which is exactly how stored grades came to disagree with their sheets and why `scripts/audit-grade-recompute-drift.ts` exists. ⚠ **Locked sheets are skipped and NAMED BACK**, never silently passed over (Hard Rule #5).

⚠ **Redistribution is whole percentage points, and the tie is broken on purpose.** The first implementation divided fractions, and `0.3 / 0.8` is `0.37499999999999994` — so a genuine 37.5 tie was resolved by representation error, landing on 37/63 while its own comment claimed 38/62. It is now largest-remainder apportionment on integers, ties going to the component already carrying more: Filipino lands on **37/63**. `__tests__/grading/component-weight-chips.test.ts` pins the client preview against the server's arithmetic, because a screen that previews 37/63 and saves 38/62 is worse than one that previews nothing.

✅ **Measured before building, and the headline was smaller than feared.** `scripts/audit-missing-component-weight.ts` (read-only) found **2 affected students in AY2026 and none in AY2025** — 348 started sheets, not one losing weight. The exposure is ahead, not behind: **no `subject_configs` row anywhere carries a zero weight**, so the school has never had a way to say "no exam", and AY2026 T3 held 3 graded entries against 124 sheets. **This is a pre-import fix, not a cleanup** — and a prerequisite for the Term 3 grading import, since every term import overwrites the year's weights (`build-grading-import.ts:343`), which is why the T2 Filipino / Global Perspectives correction script had to be written.

⚠ **Slots were ALREADY per-term and needed nothing.** `ww_totals`, `pt_totals` and `qa_total` have been per (term × class × subject) since migration 001; AY2026 already holds nine distinct exam totals for Math in Term 1 alone. Only the weights were stuck at year level. The year-wide `ww_max_slots` / `pt_max_slots` ceiling remains.

⚠ **`subjects.is_examinable` is UNCHANGED and still load-bearing** — 47 files, and it is what makes music, art and PE letter-graded. Only its label moved: the create-subject form said _"Examinable — counted toward the term/annual academic average"_, which never mentioned letters and is the wording that sent Joann to the wrong flag. It now reads **Grade type: Numeric / Letter**, matching the edit form, which had already been fixed. Renaming the column itself is deferred.

🔴 **DEPLOY ORDERING: 159 must be applied before this code ships.** The read sites select the three new columns, so the grading sheet page and the score-entry route fail against a database without them — the same trap as migration 138.

**Update (2026-09-25) — a term can switch components off, never re-split them.** Miss Joann, relayed by Mr Ace: a subject's weights are consistent across Terms 1–4; what varies per term is the slots, the max scores and whether there is an exam. So the only weights a sheet may carry are the subject's own, or `redistributeWeights` of them with components off. `isSubjectTermSplit` (`lib/grading/resolve-sheet-weights.ts`) is the gate: the sheet `totals` route refuses any other split, and the `term-weights` route lost its typed-figures form (no screen ever sent it). The "a coordinator can type the masthead's figures" allowance above is withdrawn. **And a subject weight change now carries through**: the config save's fan-out (`recomputeSyncedSheets`) re-derives every open sheet's split from the new weights, keeping only which components are off — otherwise a stored 37/63 would outlive the 30/50/20 it came from. Measured before the change (`scripts/audit-sheet-weight-overrides.ts`): **38 sheets carried their own weights, all 38 already conformed** — 37 just repeat the subject's weights, and one (AY2026 T4 Filipino, one class) is a genuine no-exam 37/63.

### KD #225

**A component's percentage divides by its FULL total — a blank slot scores zero against its max, as the grading workbooks compute it** (2026-09-26, migration 177 APPLIED, `45eb7740`).

Mr Ace asked how the Excel grading compares with the SIS on a first-day sheet: Math 40/40/20, WW 2 × 15, PT 3 × 20, QA 60, only WW1 = 14. **The SIS said 69, the workbook 64.** `componentPercentage` skipped a blank slot in BOTH sums, so the denominator shrank to whatever had been entered (14/15). Every AY2025 workbook divides by the fixed max row instead — **all 4,719 PS formulas across the 38 files are `(F10/$F$9)*100` or `F10/$F$9*100`**, row 9 holding the maxes — so a blank adds nothing and its max still counts (14/30). Mr Ace: _"when computing the grade you should get the total"_.

It had been wrong since the formula was written. Hard Rule #3 was read as "exclude a blank from the computation", and every test either filled every slot or blanked every slot — **no test had a blank beside a score**, which is the only shape where the two methods disagree. A wholly blank component is null and adds 0 either way, and QA is a single slot, so only a PARTLY filled WW or PT component moved.

- **Two copies of the formula, both changed.** `lib/compute/quarterly.ts` and the database's `grade_component_ps` (migration 152), which the `grade_entries_derive_trg` trigger runs on every save. ⚠ **A change to the formula is always a migration as well** — changing only the TS would have been silently overwritten by the trigger on the next save.
- **A component with no score at all stays null**, and an entry with nothing entered stays null rather than transmuting to 60.
- **Hard Rule #3 reworded, with Mr Ace's approval**: blank and zero stay distinct in storage, on screen and in the audit trail; for the grade they compute the same.
- ⚠ **Adding a slot now lowers every grade until it is filled** — the workbook's behaviour (a new column's max joins the total row at once). `recompute-sheet` and totals-route tests were changed to assert it.
- ⚠ **`is_na` is per ENTRY, not per slot**, so there is no way to excuse one assessment. A late enrollee's early blanks now count as zero until the registrar prorates by hand — the same as in Excel today.

**Measured before changing anything** (`scripts/audit-blank-slot-denominator.ts`, read-only): 302 stored grades would move, all downward, median 5 points, max 21; 43 crossed from 75+ to below 75. **Only 252 had actually been written by the old formula** — AY2025 T2 and T3 were imported with the workbook's own grade, which already is the right answer, and 13 other AY2025 T1 rows carried workbook or older values. Migration 177 recomputed exactly the rows whose stored grade equalled the old formula's, **locked sheets included** (Mr Ace: _"of course all sheets are affected cause our formula is wrong locked or not"_), with the derive trigger disabled around the write and a `grade_audit_log` row per changed grade carrying the approval reference (Hard Rule #5). **Verified on production:** the DB returns 64 on the example and 93 on the canonical case; 252 audit rows, every stored grade equal to its logged new value; AY2026's drift audit is clean. AY2025 still shows **10 drift rows that disagreed with the old formula too** — history (one is KD #176's SCI · Discipline 1 · T2), untouched.

✅ **Found while writing 177, fixed by migration 178 (APPLIED 2026-09-27):** the derive trigger (154) took weights only from `subject_configs`, never the sheet's own (KD #218, 159), so a no-exam 37/63 sheet would have been re-derived at 30/50/20 on every save. It is now sheet-first, one hop, like the TS resolver. Nothing stored had been affected: all 24 graded entries on the 38 sheets with their own weights gave the same grade either way.

**Update (2026-09-27) — the registrar can excuse a slot for one student (proration), migration 179 APPLIED.** 177 removed the old behaviour that had been doing proration by accident — the grid's "Late" badge literally said "proration is automatic". Now the registrar (academic*coordinator and above) clicks a student's name on the grading sheet: **"Counted assessments"** lists every WW/PT slot ticked; unticking one takes it out of that student's score AND total. `grade_entries.ww_excused / pt_excused int[]` hold 1-based slot numbers; `grade_component_ps` / `compute_quarterly` take them (TS and SQL agree), the trigger refuses a change from a non-registrar and a score in an excused slot, and drops slot numbers past the sheet's slot count. Writes go through `PATCH /api/grading-sheets/[id]/excused` (locked sheet = data-entry correction + `grade_audit_log`). Deliberately **manual** — Mr Ace: *"let them untick a slot"\_; slots carry no dates, so nothing can decide automatically what came before a child joined. The exam is not in the list (a missed exam is the whole-entry N/A).

**Update (2026-09-27) — a grade is only judged once the row is complete** (`lib/grading/row-complete.ts`, no migration). Since blanks score zero, a quarterly grade exists from the first score and reads low. So: the grid colours a quarterly grade only when every counted slot and the exam have a score; the Graded counts (sheets list and the sheet's stat card) count only complete students; the lookup still lists and compares everyone, but an incomplete current term's change is grey, never flagged, carries a **"Not fully graded"** badge, and its point on the chart is a dashed grey segment into a hollow grey point (`TrendChart lastPointProvisional`). Mr Ace's correction, worth keeping: the first attempt removed the comparison for incomplete rows — _"you just completely remove monitoring for lookup … you just need to dont flag them red"_.

### KD #230

**A "Term 4 framework" sheet type — Secondary 4's Term 4 is graded 50% best of T1–T3, 20% teacher's recommendation, 30% revision task / mock exam** (2026-10-07, commits `85d151ef`..`fe5de6a0`, migrations 183 + 184 written, NOT yet applied to production).

**Why.** Sec 4 has about two weeks of Term 4 before O-Level study leave (5 Oct – 10 Nov 2026), so the school grades it by its own "Term 4 Grading Framework for Secondary 4 Students" instead of the usual WW/PT/QA. AY2025 ran it in Excel; AY2026 grades it in the SIS. Excel needs cross-workbook name lookups to pull each student's earlier terms, and a report card went out with wrong grades on 2026-10-06 while the grading was in Excel.

**The rule.** The T4 total = 50% the student's **best of their T1–T3 term averages** + 20% the teacher's recommendation out of 30 + 30% a revision task / mock exam out of 100; the total goes through the usual DepEd transmutation. Final Grade is unchanged (20/20/20/40).

- **Term average** = the mean of the student's T1–T3 quarterly grades over **examinable subjects only** (the same set as the General Average), 1 decimal. An N/A term is skipped (proration for late enrollees). The value is the **same in every subject** for the student. Ties go to the later term. A subject counts once per term for a student who moved class: the non-withdrawn enrolment's row wins.
- **Worked example.** Best 86, recommendation 24/30, task 70/100 → 43 + 16 + 21 = 80 → transmutes to 87.

**Decided with Mr Ace, 2026-10-07.** "Per student" means the whole-term average, not per subject. The same conversion as every sheet. _"Of course update if approved"_ — the best-term value is a **live cascade**, locked sheets included. The name is the school's own title, "Term 4 framework" ("Holistic grading" rejected). Bulk create is unchanged (a framework sheet is created one at a time). O-Level vs non-O-Level is not an SIS concern. Non-examinable subjects are untouched.

**Build — reuse the fixed shape, change no formula.**

- `grading_sheets.sheet_type` (`'standard'` | `'term4_framework'`) plus a CHECK pinning the fixed shape: `ww_totals {100}`, `pt_totals {30}`, `qa_total 100`, weights .50 / .20 / .30. The WW slot holds the best term average (out of 100), PT the recommendation (out of 30), QA the task. **`lib/compute/quarterly.ts`, `compute_quarterly` and the derive trigger are unchanged — Hard Rule #1 is untouched.**
- **Migration 183:** the column, `student_best_term_average(student, ay)`, `best_term_averages_for_sheet(sheet)` (both service_role only), and `sync_grading_sheets_from_config` now skips framework sheets.
- **Migration 184:** BEFORE trigger `grade_entries_best_term_fill_trg` (sorts before the derive trigger) fills the WW slot and **refuses a typed value or an excusal** (SQLSTATE `HFT4F`), writing a `grade_audit_log` row (`system: best term average`, field `ww_scores[0]`) when the value moves. AFTER trigger `grade_entries_best_term_cascade_trg` re-touches the student's framework entries when a T1–T3 `quarterly_grade` or `is_na` changes; it has **no column filter**, because `quarterly_grade` is set by the derive trigger and is never in the caller's SET list; it skips framework source sheets and null-grade inserts. `grade_entries_audit()` skips the system-owned WW slot on framework sheets so `audit_log` never attributes it to the calling teacher.
- **App:** `lib/grading/term4-framework.ts`; the create form has a "Sheet type" choice; routes refuse totals / weights / excusal edits on framework sheets and the term-weights route skips them; the grid headers read "Best term average / Teacher's recommendation / Revision task / Mock exam", the best-term cell is read-only with the source term as a hint.
- SQL test: `supabase/tests/term4_framework_test.sql` (local stack, rolled back).

**Final-review fixes (2026-10-07, 183/184 edited in place — local only, never production).**

- **Term 4 only.** `POST /api/grading-sheets` refuses a framework sheet on any term but Term 4; the create form offers the option only when Term 4 is picked (and falls back to Standard when the term changes). In the database, a framework sheet is never a source of the best term average (`student_best_term_average` reads `sheet_type = 'standard'` sheets only) and the cascade writes Term 4 rows only.
- **Creating over an existing Term 4 sheet.** Creating a section makes a standard sheet for every subject × term, so the class usually has one already. Create now **converts that sheet in place** when nothing was ever entered on it (the removal test, `lib/grading/sheet-removal.ts`): one UPDATE to the fixed shape and weights (activity labels cleared), then its rows reset to blank so the fill trigger writes the best term average; audited as `sheet.create` with `converted_from: 'standard'` and the previous shape. A standard sheet with scores is refused in plain English; a second framework sheet is refused; a remaining unique clash reads "This class already has a sheet for this subject in this term." The audit row records the inserted shape, not the client's totals.
- **Removable.** On a framework sheet the system-filled WW slot and the derived figures are not "entered data", and the fill's `grade_audit_log` rows (`system: best term average`) are not history — so the sheet can be removed while no person has entered a recommendation, task score, letter, excusal or N/A. Removal deletes those system rows first (their FK holds the sheet) and keeps their content in the `sheet.delete` audit row.
- **No label prompts.** The first-score label gate (client and the entries route) skips framework sheets; the Activity labels drawer shows the fixed names.
- **Publish readiness.** A row with only the best term average already has a quarterly grade (50% of the total), so the `grades_missing` check is satisfied by it; an unfinished framework sheet is still caught by `sheets_unlocked`.
- A student with no grade row yet (added after the sheet was made) shows "Not filled yet" rather than "No earlier grades".

⚠ **Known gaps.** (1) The derived `quarterly_grade` change on a **locked** T4 row is not itself written to `grade_audit_log` — the WW change that caused it is. (2) A student with no T1–T3 grades shows "No earlier grades" and never counts as graded; the registrar resolves it.
