## Markbook — core grading mechanics, sheet config, slot metadata, bulk lock

### KD #3

Teacher assignments in `teacher_assignments(user, section, subject, role)` — `form_adviser` or `subject_teacher`. Gates grading-sheets list + section comments.

### KD #4

Weights per `(subject × level × AY)` in `subject_configs`; Primary 40/40/20, Secondary 30/50/20; never hardcoded.

### KD #5

Max 5 WW + 5 PT slots per sheet; max 50 students per section.

### KD #6

Annual grade = `T1×0.20 + T2×0.20 + T3×0.20 + T4×0.40`, 2dp. `lib/compute/annual.ts`.

### KD #99

`sync_grading_sheets_from_config(p_config_id uuid)` RPC (migration 052b). Grading sheet `ww_totals/pt_totals/qa_total` columns are denormalized copies of subject_configs at sheet-creation time. When SIS Admin updates `ww_max_slots`, `pt_max_slots`, or `qa_max` on a `subject_config`, this RPC brings all **unlocked** sheets linked to that config into sync — locked sheets are never touched (Hard Rule #5). Resize behaviour: ww/pt arrays extended → new slots default to max score 10; truncated → trailing scores/totals dropped; `qa_total` replaced unconditionally with the new `qa_max`. Called by `PATCH /api/sis/admin/subjects/[configId]` immediately after the DB UPDATE, before the audit log write. Returns `jsonb` with `rows_synced` count for the audit trail.

### KD #105

WW/PT slot metadata extension — date administered + optional page# (migration 057). `grading_sheets.slot_labels` JSON shape migrated from bare strings to `{ label, date, page }` objects per WW/PT slot; QA stays a single nullable string. Migration 057 one-shot coerces existing string entries to `{ label: "...", date: null, page: null }`. `ActivityLabelsForm` / `LabelRow` gain 3-column layout (Description · Page # · Date administered) + "Use today" quick-button. `SlotChip` renders date + page conditionally, omitting missing fields; muted styling when label set but date not. `saveLabel` PATCH accepts `Partial<SlotMeta>` and merges server-side (field-level blur doesn't clobber other fields). `SlotMetaPatchSchema` in `lib/schemas/grading-sheet.ts`. Publish-readiness `GET /api/sections/[id]/publish-readiness` adds a `slot_dates` soft-warning block (KD #28): cross-references `grade_entries.ww_scores/pt_scores` arrays against `slot_labels` date fields; surfaced as amber `ChecklistRow` with `CalendarDays` icon in `components/admin/publish-window-panel.tsx`. **Update (2026-06-03):** that `slot_dates` publish-readiness soft-warning was **removed** from `GET /api/sections/[id]/publish-readiness` + `<PublishWindowPanel>` — administered dates are a score-record concern, not report-card-related (KD #75 audit).

**Update (2026-06-09) — slot label/date do NOT gate score-cell entry.** An earlier version of this KD stated "both `label` AND `date` must be set to unlock score cells." This gate does not exist in the code. Verified: `components/grading/score-entry-grid.tsx` line 538 — `const inputsDisabled = r.withdrawn || r.is_na || readOnly` — the only conditions that disable a `<ScoreInput>` cell are: row is withdrawn, row has `is_na` set, or the sheet is `readOnly` (locked). Slot `label`/`date`/`page` are **optional metadata** rendered in the column-header chip and on the score record; they are recommended for completeness but **do not gate score entry**. The per-cell unlock logic is unchanged from the original WW/PT/QA implementation. The prior Update (2026-06-03) line "The label-AND-date cell-unlock gate described above is unchanged" was also incorrect and is superseded by this note.

**Update (2026-06-09, pt 2) — soft "unlabeled scored slot" flag + "Ongoing" date value.** HFSE confirmed **subject teachers own both the activity labels AND the scores** (same person → no cross-role bottleneck). Decision: still **NOT a hard gate** on scoring (labels aren't report-card-rendered; hard-blocking the core action for a record-quality nicety is disproportionate; no observed evidence labels go missing) — instead a **soft signal**: a WW/PT slot with ≥1 score but **no description** is flagged in the `ScoringGuide` (`components/grading/score-entry-grid.tsx`) — the `ActivityRow` shows an amber `AlertTriangle` "Needs a label" (was muted "No label set"), and the collapsed summary appends "· N need a label". "Has a score" is computed over the **full roster** (`rows`, not `visibleRows`) so the flag doesn't flicker under filtering. Scoring is never blocked. **"Ongoing" date-administered value:** HFSE's workbook uses both real dates AND the literal "Ongoing" for the date administered, so `SlotMetaSchema.date` now accepts `'Ongoing'` OR `YYYY-MM-DD` (`lib/schemas/grading-sheet.ts`); the labels PATCH route's inline `sanitizeDate` (`app/api/grading-sheets/[id]/labels/route.ts` — note: the route sanitizes inline, it does NOT parse via `SlotMetaPatchSchema`) passes `'Ongoing'` through; the editor (`activity-labels-dialog.tsx`) gained a reusable `DateAdministeredField` (DatePicker + an "Ongoing" toggle ↔ amber pill + clear); the read-only chips already render "Ongoing" (the `formatChipDate` regex no-matches → returns the raw string). UAT note: the academics alignment doc A-06 (which says labels are optional) stays correct — labels remain optional, just now softly flagged when a scored slot lacks one.

**Update (2026-07-24) — the soft-only decision above is REVERSED. A hard gate now exists, scoped to a slot's first score only.** Mr Ace revisited this with a new, concrete motivation the earlier decisions didn't have: HFSE's teacher-owned SOW _feature_ was built once and then fully removed (KD #108/#110 — too much upkeep, drifted from what teachers actually taught), so there's no live curriculum-plan record left in the system; the per-slot description is now the closest thing to letting a coordinator sanity-check "what was actually taught, and roughly when" against pacing. Before shipping, a live-data check found 1,662 existing scored-but-unlabeled `(sheet, slot)` pairs (mostly in the historical AY2025, only 29 in the live AY2026) — driving the specific shape of the reversal below, so the fix doesn't retroactively punish that backlog.

**What actually gates now:** a WW/PT/QA slot's very first score (roster-wide — the first time ANY student gets a score there) is intercepted by a dialog requiring Description + Date administered (WW/PT) or Description only (QA) before the score is accepted. **A slot that already has ≥1 real score — from before this shipped, or from any student since — is permanently grandfathered, gate-exempt, no backfill.** Editing an already-scored slot never gates, only a slot's genuine first entry does. Page # still never gates. `'Ongoing'` still counts as a satisfied date.

**Enforced in two places, not just the UI** (closing the exact gap the 2026-06-09 note above was correct about at the time): the shared predicate `slotMetaSatisfied`/`slotRosterScored` (`lib/grading/first-score-gate.ts`) is imported by BOTH the client (`components/grading/score-entry-grid.tsx` — `commitScore` intercepts the three `ScoreInput onCommit` sites and opens `components/grading/first-score-label-dialog.tsx`) AND the server (`app/api/grading-sheets/[id]/entries/[entryId]/route.ts` — an `if (!sheet.is_locked)` block rejects a genuine first score with `422 label_required` unless the same request also supplies a `slot_label` to satisfy it). **Gate applies only to the unlocked, direct-entry path** — the locked-sheet change-request (Path A) and correction (Path B) flows (Hard Rule #5) are untouched by design, proven by test (a call-count spy on the gate's own roster query, not just code inspection) to never fire on either. One combined write: the label merges into `slot_labels` (via `lib/grading/slot-label-sanitize.ts::mergeSlotLabel`, sharing the same sanitize rules — `'Ongoing'`/ISO/trim/cap — the labels route uses) BEFORE the score write, in the same request, not two separate PATCHes. No schema/migration change — reuses the existing `slot_labels` jsonb column as-is.

The client-side check deliberately reads `savedRowsRef` (server-confirmed roster state), never the file's pre-existing `wwScored`/`ptScored` — those are memoized on `rows`, which updates optimistically on every keystroke, so by commit time they'd already read the just-typed slot as "scored" and the gate would never fire.

Migration `057_grading_sheet_slot_meta.sql`'s header comment ("A slot unlocks for score entry only when BOTH label AND date are set") predates all of this — it was written aspirationally, never actually implemented, and the 2026-06-09 note above correctly caught that gap. It's now roughly true again, minus the first-score-only/grandfather nuance it doesn't describe. Spec: `docs/superpowers/plans/2026-07-24-first-score-label-gate.md`.

**Update (2026-07-24, pt 2) — Activity labels panel is a drawer, not an always-expanding inline block.** `ScoringGuide` (`components/grading/score-entry-grid.tsx`) previously expanded in place above the score grid — with all 10 WW/PT slots + QA rendered as full editors, it ate ~400px of scroll before the roster even started, regardless of class size. The panel's toggle row is now a fixed-height trigger strip (same eyebrow/summary/amber-flag content) that opens a `Sheet` (`sm:max-w-xl md:max-w-2xl`, wider than the shadcn default so the Description/Page/Date row has room) containing the identical grouped Written Works / Performance Tasks / Quarterly Assessment `ActivityRow` editors — same autosave-on-blur, same soft "needs a label" flag. No change to save/commit behaviour, only where the editors render. Alongside this, `DateAdministeredField` (used here and by `FirstScoreLabelDialog`) was simplified from two floating buttons (a full-width `DatePicker` fighting a text "Ongoing" button for space — the original cramping culprit) to a `DatePicker` + a plain **"Ongoing" checkbox**: checking it sets the value to `'Ongoing'` and disables the date picker (discarding its value, same as the old "clear and switch" behaviour); unchecking clears back to empty. No schema/API change — same `'' | 'Ongoing' | 'YYYY-MM-DD'` value contract.

### KD #131

Bulk manual grading-sheet lock (Sprint 57, 2026-06-06; assumptions register M5). HFSE confirmed grading sheets have due dates → keep **both** auto-lock-by-date (cron `lock-overdue`) **and** manual locking; the gap was bulk. New **`POST /api/grading-sheets/bulk-lock`** (`{ ids: string[] }`, cap 200) mirrors the single-sheet lock route exactly — same `requireRole(['registrar','school_admin','superadmin'])`, locks only the **unlocked** ids (already-locked skipped, not errored), one `sheet.lock` audit row per newly-locked sheet, `invalidateDrillTags('markbook', ay)` once; returns `{ locked, skipped }`. UI: a select column + **"Lock selected"** bulk-action-footer button on the grading list (`grading-data-table.tsx`, registrar+ only, unlocked rows only, `AlertDialog` confirm noting post-lock edits need the change-request flow). The unified `<DataTable>` shell (KD #84) gained optional `SelectionConfig.enableRowSelection(row)` (per-row gate) + `selectionResetSignal` (clears the footer after the action) — additive, existing consumers unaffected. Hard Rule #5 preserved (locking needs no approval — it ENABLES the post-lock change-request flow). No migration.

### KD #158

Grading sheet shows the **live** subject teacher, not the denormalized column (2026-07-28; no migration). `/markbook/grading/[id]`'s hero read `grading_sheets.teacher_name` — a legacy text column written once at sheet creation and never updated when assignments change, so it **drifts** where populated and is simply **empty across AY2026**, rendering nothing. The fix is not "add a missing line" but "stop reading a column that cannot be right."

- **New pure resolver** `lib/markbook/subject-teacher.ts::buildSubjectTeacherNameMap` (+ `subjectTeacherKey`) resolves `(section, subject)` → display names from `teacher_assignments` (`role='subject_teacher'`) joined to `lib/auth/staff-list.ts::getStaffDisplayNameById()`. Same authoritative-vs-mirror choice as `buildFormAdviserNameMap` in `lib/markbook/masterfile.ts`. Extracted so it is unit-testable without mocking the RSC's Supabase call graph (`__tests__/markbook/subject-teacher-map.test.ts`).
- **Returns ALL teachers for a pair, not the first.** The unique index `teacher_assignments_subject_teacher_unique` is on `(teacher_user_id, section_id, subject_id)`, so co-teaching is permitted — silently dropping a second name would be a hard-to-notice wrong. The grading _list_ still picks first-write-wins (a table cell is tight); the detail hero has room and comma-joins.
- **Empty state is explicit** — "No subject teacher assigned" (muted italic), not silence. Expect this to be the state everyone sees for a while: teacher accounts haven't been created for the AY2026 migration, so `teacher_assignments` has no `subject_teacher` rows to resolve. That's a data-loading gap, not a code gap — this populates itself once the accounts exist, no further work. No "assign" link yet, deliberately: it would land on a page where the task can't be completed until those accounts exist.
- Spec/plan: `docs/superpowers/{specs,plans}/2026-07-28-grading-sheet-subject-teacher*`.

### KD #176

**A subject config's slot/score numbers are a CEILING, not a broadcast value** (2026-08-01; migrations 107 + 108). Two defects in `sync_grading_sheets_from_config`, both found while triaging the 2026-07-31 academics training.

**1. It resized denominators and never recomputed the grades.** The RPC propagates `ww_max_slots`/`pt_max_slots`/`qa_max` to every unlocked sheet for a config — all four terms, every section, every level — and resizes the matching `grade_entries` arrays. It did **not** touch `ww_ps`/`pt_ps`/`qa_ps`/`initial_grade`/`quarterly_grade`, and being a SQL function it cannot: `lib/compute/quarterly.ts` is the only place the formula lives (Hard Rule #2) and a second copy of the transmutation table in PL/pgSQL is not acceptable. The stored `quarterly_grade` is what the report card **prints** (`build-report-card.ts` reads it directly), so this produced wrong printed grades that stayed wrong until someone happened to re-save a score on that sheet.

Fixed by moving the recompute into TypeScript (`lib/grading/recompute-sheet.ts`, extracted from the per-sheet totals route, which was the only correct implementation and is now the shared one). Migration 107 makes the RPC return `sheet_ids`; the caller recomputes exactly those. **Reading the ids back from the RPC rather than re-querying closes a real race** — a sheet locked between the two would be resized and then filtered out of the recompute, leaving a stale LOCKED sheet, which is the worst case since those feed published cards. The caller prefers `sheet_ids` and falls back to its own query, so it is correct in either deploy order. Sheets are re-read at recompute time and any now-locked one is skipped and reported (Hard Rule #5 — a background recompute must never be a post-lock edit). The sync stopped being best-effort: failure now returns 500 with a pointer to the new `POST /api/sis/admin/subjects/[configId]/resync`, which exists because `subjectConfigUnchanged` short-circuits a re-save of identical values — after a partial failure the operator's instinct (press Save again) returns success while doing nothing.

**Measured before fixing.** `scripts/audit-grade-recompute-drift.ts` (read-only, `--ay`, `--all`, exits non-zero on drift) found the config-sync bug had **not** bitten production — all unlocked AY2026 sheets were clean. One locked sheet did drift (SCI · Discipline 1 · T2, 29 students), from the **grading backfill import**, not this RPC. Critically the fix direction was the opposite of the obvious one: all five stored values reproduced exactly under the _sibling_ sheets' totals, so the **grades were right and the totals were wrong**; recomputing would have pushed 29 real students down. Repaired via `scripts/backfill/gen-ay2026-sci-discipline1-t2-totals-correction.ts`, which refuses to emit SQL unless that reproduction still holds. **The audit tool must skip non-examinable subjects** — their `quarterly_grade` is a band-representative integer (95/87/82/70) standing in for a letter, not a formula output; comparing them produced ~700 false positives on AY2025 and one wrong diagnosis before it was caught.

**2. It broadcast values over deliberate per-section settings.** `qa_total = v_qa_max` was written unconditionally to every unlocked sheet on **every** save, including saves that only touched a slot count. HFSE agrees a Scheme of Work before each AY and that broadcast is the intended workflow (Chandana, 2026-07-31) — but mid-year changes happen, "rare but not impossible", and there the broadcast reverts a per-section exam total (a Secondary paper out of 140 while the level sits at 100) silently, with the teacher who set it never told.

Two rules, both **no-ops at the start of an AY** so the SOW workflow keeps zero friction: (a) `findTruncationBlockers` refuses a slot reduction that would erase entered marks — 409 naming components and 1-based slot numbers, a `0` counting as a real mark per Hard Rule #3, because a score cannot be recovered _from_ an audit row so blocking beats logging; (b) `resolveQaTotal` only overwrites a sheet still holding the **old** `qa_max` — a customised sheet is left alone. Migration 108 stops the RPC writing `qa_total` entirely: **SQL owns array shape, TypeScript owns values.** The caller snapshots each sheet's prior `qa_total` _before_ the RPC, so it is correct in either deploy order.

**Do not "fix" this by adding per-subject WW/PT default max scores.** Measured against prod: max scores follow a **level ladder** (AY2025 English — WW `[10,10,10]` at P1–P2, `[15,15,15]` at P3–P4, `[20,20,20]` at P5–P6 and Secondary; PT `[30,30,25]` across Secondary), with sections inside a level still differing. A single per-subject default is wrong at nine levels in ten and would recreate the `qa_max` problem these rules exist to contain.

**Resolved 2026-08-01 — the sheet is the right place, and SIS Admin keeps only the weights and the ceiling.** Per-subject × level configs were considered and rejected too: the sheet's Totals editor already sets max scores, the exam total and any slot count at or below the ceiling, so per-section configuration is a solved problem in the wrong place rather than a missing feature. Accepted cost: that editor is coordinator+ only, so a genuine mid-year SOW change means opening each affected sheet — acceptable while changes stay rare, and the trigger to revisit is a real level-wide mid-year revision, at which point the answer is **bulk totals editing**, not per-level configs. The subject form now states its blast radius ("N grading sheets across M classes will be updated. Locked sheets are not changed.") from `lib/sis/subjects/sheet-impact.ts`, and its old warning that "scores in removed slots will be lost" was corrected — that stopped being true when the truncation refusal landed. Full reasoning in `docs/sprints/development-plan.md` under the academics-training section.

### KD #179

**At-risk compares the components, not just the term grade — and slot identity is deliberately never built** (2026-08-03; no migration). Koh described a student who scored 90 in Term 1 and dropped in Term 2; asked to be precise, Hermilita added "not only for the quizzes, but also for exam, for overall". The Alerts column compared `quarterly_grade` alone, which is the one of those three that can hide the other two: written work can collapse while the exam rises to cover it, and the alert never fires.

- **`loadPriorTermGrades` now selects `ww_ps`, `pt_ps`, `qa_ps` alongside the term grade.** Same query, same joins, no extra round trip. `ALERT_METRICS` drives four comparisons and the dialog names which one moved.
- **The ±5 threshold was four separate literals** — the comparison, the chip's aria-label and three lines of dialog copy — which could silently disagree after any one edit. One exported `GRADE_ALERT_THRESHOLD` now. It stays a **code constant**, following `AT_RISK_ATTENDANCE_THRESHOLD_PCT`: a display heuristic for drawing a teacher's eye, not a policy HFSE has adopted. Move it to `school_config` the day they tell us what the number should be — a tunable knob nobody has an opinion about is just another empty admin field.
- **The mid-term half: `outlierSlotIndices`.** No cross-term comparison can answer "she bombed last week's quiz" — that happens long before a term grade exists. This flags a score at least 10 points below that student's own average across the other scored slots on the **same sheet**, normalised by each slot's own maximum, silent below three scored slots, and blind to blanks (Hard Rule #3). No query and no slot identity: every number is already on screen. Amber, never the red used for a real error; the legend under the sheet appears **only when something is flagged**, because a permanent legend for an invisible marker is a promise the sheet is not keeping — `lib/attendance/insights-watchlist.ts` records a watchlist deleted for exactly that.

**Do not build same-slot-across-terms comparison.** Slots are array positions with index-positional free-text labels; the arrays resize per sheet; KD #105 records 1,662 scored-but-unlabeled pairs that are permanently grandfathered; and the labels carry page numbers — i.e. sequential curriculum, not repeated instruments. Even executed perfectly, comparing a fractions quiz to a geometry quiz is noise dressed as signal. **Components are normalised percentages and comparable; slots are not.**
