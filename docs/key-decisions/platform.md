### KD #32

Dates: ISO 8601 UTC in storage/transit; local formatting at render via `toLocaleString('en-SG')`. No `dayjs`/`date-fns`/`moment`.

**SGT calendar-date rule (2026-06-03).** School-calendar values — term windows, attendance dates, `enrollment_date`/`withdrawal_date` — are date-only **Singapore** (UTC+8) dates. Computing "today" as `new Date().toISOString().slice(0, 10)` takes the **UTC** calendar date, which is the _previous_ day during the 00:00–07:59 SGT window — so comparing a UTC "today" against an SGT term window mis-resolves the term at a boundary (e.g. a 7am-SGT enrolment on a term's first day reads as the prior break), and a UTC-sliced display date shows one day off. **Canonical helpers live in `lib/dates.ts`: `sgToday()` (SGT `yyyy-MM-dd`) and `sgDate(iso)` (SGT date of a UTC timestamp).** Use them anywhere a "today" or timestamp→date value is **compared against, or stored as, a school-calendar date** — never raw `.toISOString().slice(0,10)`. Storage/transit timestamps stay full UTC ISO (the rule above is unchanged). Adopted across the term resolver (`getEnrolmentPosition`), section-transfer term-of-date, enrollment/withdrawal date stamps (stage + section-students + sync routes), the attendance writer's today gate, the attendance current-term pages, and the movements feed. `lib/evaluation/ptc-resolver.ts::sgToday` re-exports from `lib/dates` for back-compat. **Deliberately not changed** (cosmetic / not calendar-boundary): dashboard date-range defaults, p-files expiry comparisons, and the seeders. **Update (2026-06-09) — a code audit found two of those weren't actually cosmetic and were switched to `sgToday()`:** the dashboard **term-resolution** source `lib/dashboard/windows.ts` (feeds `resolveCurrentTerm` → every dashboard's "this term" default) + `lib/markbook/dashboard.ts` / `markbook/page.tsx` / `grading/new/page.tsx` (term-by-date), and the p-files **status-write** path `lib/p-files/freshen-document-statuses.ts` (auto-expire/revive on SGT expiry dates) — all mis-resolved/mis-wrote in the 00:00–07:59 SGT window. Genuinely cosmetic display/email date filters (`lib/sis/dashboard.ts` calendar events, `lib/p-files/queries.ts` promise-active, `email-pfile-reminder.ts`) + the seeders stay raw.

### KD #147

Module-ownership & historical-truth-vs-current-truth rule — Admissions ↔ Records ↔ P-Files. Full model in **`docs/context/22-module-ownership-truth-model.md`** (read it before changing any write path touching `ay{YY}_enrolment_{applications,status,documents}` or `public.section_students`). **Principle:** _historical truth_ is append-only, never rewritten (Hard Rule #6); _current truth_ is owned by exactly one module post-enrolment, the others display a **read-only mirror**, and status moves **forward only** (an Enrolled student is never pushed back into the funnel). **Four participants, one shared student record:** (1) **Admissions** owns the application record + pre-enrolment doc validation — **historical/read-only once Enrolled**; (2) **Shared Student Profile** = the `ay{YY}_enrolment_applications` identity row (name/DOB/gender/nationality/address/passport/pass/parents/contacts), **editable from Admissions OR Records** (one record; name also denormalized into `public.students` — keep in sync); (3) **Records** owns the post-enrolment **academic lifecycle** on `section_students` (status/date/section/level/attendance/grades/evaluation/withdrawal/re-enrol) — `applicationStatus` is its mirror, kept in sync by the Records→Admissions cascade; (4) **P-Files** owns the post-enrolment **document lifecycle** (`{slot}Status/Url/Expiry` + append-only `p_file_revisions`/`p_file_outreach`), reads enrollment/profile only. **Two temporal handoffs at enrolment:** academic→Records, documents→Admissions(pre)→P-Files(post). **Enforcement (write-layer):** **Lock #1** — the admissions stage editor (`app/api/sis/students/[enroleeNumber]/stage/[stageKey]/route.ts`) freezes stage-status edits once `applicationStatus==='Enrolled'`, via the shared `isAdmissionsStageFrozen` (`lib/schemas/sis.ts`, also consumed by the enrollment-tab UI so they can't drift). **Exception: `supplies` + `orientation`** happen after enrolment, so they stay editable until **finalized** (supplies `Claimed`/`Cancelled`, orientation `Finished`/`Cancelled`) then lock (422 `stage_finalized`, forward-only); every other stage 422s `enrolled_frozen`. `Enrolled (Conditional)` stays fully editable until it resolves; the withdrawal/re-enrol cascades write via the section-students route, not this editor, so unaffected; **Lock #2** — the document-validation PATCH (`app/api/sis/students/[enroleeNumber]/document/[slotKey]/route.ts`) 403s the `admissions` role on an **enrolled** student (docs are P-Files') and `p-file` on an **un-enrolled** one (validation is Admissions'); `registrar`/`superadmin` act either side (KD #37). **Amends KD #97:** Records is no longer read-only on the **shared profile** (profile/family become editable from Records via the existing `/profile` + `/family/[parent]` routes) — it stays read-only on the **application-history** axis. Cross-ref Hard Rule #6 (append-only), KD #67/#83 (transfers/movements as historical truth), KD #59/#70 (the two applicationStatus columns + doc-validation queue split), KD #90 (unsynced gap), KD #31/#71 (P-Files enrolled-only). No schema change.

### KD #150

`applicationStatus` is the application **OUTCOME** (append-only); current state lives on `section_students.enrollment_status` (2026-06-26). **Amends KD #147** — narrows its "`applicationStatus` is a current-state mirror kept in sync by the Records→Admissions cascade." **The bug:** the one column carried two meanings — the application's final _outcome_ and the student's _current_ status. They diverge the moment a student **enrols then withdraws**, and the post-enrolment withdrawal route was overwriting `applicationStatus → 'Withdrawn'`, **erasing the fact the application succeeded** (violating KD #147's own "historical truth is append-only" principle) and double-listing the student in **both** the Admissions closed-applications archive **and** Records withdrawn. **The model:** `applicationStatus` = the OUTCOME / furthest-forward status reached (`Enrolled` / `Enrolled (Conditional)`, or a genuine **pre-enrolment** terminal `Cancelled`/`Withdrawn`), **never overwritten by a post-enrolment event**; `section_students.enrollment_status` (`active`/`withdrawn`/`late_enrollee`) is the single source of truth for current state. **Change:** the section-students withdrawal route (`app/api/sections/[id]/students/[enrolmentId]/route.ts`, via extracted pure `buildWithdrawalAdmissionsPatch`) sets only `enrollment_status='withdrawn'` + `withdrawal_date`/`reason` — **no `applicationStatus` write**. Re-enrol still writes a _forward_ `applicationStatus='Enrolled'` (restoring a forward status, not a terminal cascade). **Pre-enrolment terminal flips (stage route, never-enrolled apps) UNCHANGED** — a real outcome. **Consumer rule (audited all 17 terminal readers):** anything detecting _"currently withdrawn"_ must read `section_students.enrollment_status`, NOT `applicationStatus`. Outcome-readers left as-is → the Admissions **closed list + cancellation/terminal counts become cleanly pre-enrolment-only** (more correct). Current-state readers switched: **`lib/supabase/admissions.ts::fetchAdmissionsRoster`** excludes currently-withdrawn via `filterWithdrawnFromRoster` (**critical — without it the bulk "Sync from Admissions" would _reactivate_ a withdrawn student** now that they read `'Enrolled'`); **`lib/sis/process.ts::resolveIsWithdrawn(applicationStatus, ssEnrollmentStatuses)`** is dual-signal + **transfer-aware** (a transfer leaves an old `'withdrawn'` row beside a new `'active'` one — KD #67 — and must NOT read as withdrawn; withdrawn only when no active/late row coexists). **Parent portal (`getAllStudentsByParentEmail`) deliberately UNCHANGED** — decision: **include** withdrawn students (the external `/api/parent/v2/*` surface), since report-card visibility is independently gated by the publication window (KD #10). **Display:** `components/sis/student-status-badges.tsx` — read-only `Application Outcome: {outcome}` + `Current Status: {humanized enrollment_status}`; on the Records student detail (both) + Admissions applicant detail (outcome-only — `enrollment_status` not in scope there). **Seeder:** enrolled-then-withdrawn personas keep `applicationStatus='Enrolled'` (+ `enrollment_status='withdrawn'`); pre-enrolment terminals keep their terminal status (surfaces on a fresh test-AY reseed). **Effect:** an enrolled-then-withdrawn student now appears in Records withdrawn but **not** the Admissions closed list. **No migration, no backfill** (a population check found **0** corrupted rows across AY2025/26/27 — the corruption was latent, prevented go-forward). **Latent/documented:** `lib/sync/students.ts::syncOneStudent`'s `applicationStatus==='Withdrawn'` skip-guard is now incomplete (commented; not hittable today — bulk path protected upstream by `fetchAdmissionsRoster`, direct callers operate only on the unsynced queue). Spec/plan: `docs/superpowers/{specs,plans}/2026-06-26-application-outcome-vs-current-state*`. Cross-ref KD #147 (module ownership), KD #67 (transfers), KD #59/#70 (two `applicationStatus` columns + closed list), KD #10 (publication-window gate), Hard Rule #6 (append-only).

### KD #155

### KD #166

**Capability layer — the vocabulary is code, the grants are data** (2026-07-30; migrations 101 + 102). Role was read directly in seven independent layers (28 `ROUTE_ACCESS` prefixes, 111 `requireRole` sites across 11 distinct role-set combinations, 35 inline narrowings, 8 route-group layouts, 53 page guards, 38 role-derived flags under 25 different names, 31 nav entries). Two real HFSE needs cannot be met inside that model, and both are about a **person**, not a role:

1. **One person validates documents on BOTH sides of enrolment.** The rule that stopped them — KD #147's ownership handoff, `admissions` before Enrolled and `p_file_officer` after — is **correct and is unchanged**. But it was welded to a role NAME in `app/api/sis/students/[enroleeNumber]/document/[slotKey]/route.ts`, and a person holds exactly one role.
2. **`school_admin` does two jobs** (academics oversight + office admin) that no single role name describes.

**The shape.** `lib/auth/capabilities.ts` (pure, client-safe) declares the vocabulary — 8 `RESOURCES` × their actions — plus `DEFAULT_ROLE_CAPABILITIES`. `public.role_permissions` (migration 101, `(role, capability)`) holds who actually has what, editable by a superadmin at **`/sis/admin/roles`** (`components/sis/role-permissions-editor.tsx`, `PATCH /api/sis/admin/role-permissions`). `lib/auth/permission-map.ts` is the server-only read; `lib/auth/require-capability.ts` is the route gate.

- **`requireCapability` is signature-identical to `requireRole`** — same return shape, same status codes — so migrating a route is a one-line swap and `auth.user.id` / `auth.role` keep working. That is deliberate: it makes this **additive**, not a migration all ~90 remaining `requireRole` sites have to finish. `auth.role` is still returned because 35 sites branch on identity after the gate, which is a legitimately different question from permission.
- **The parity rule.** `DEFAULT_ROLE_CAPABILITIES` reproduces today's behaviour **exactly** and seeds migration 101, so applying it changes nothing. Every grant cites the site it was read off, and **where today's behaviour is asymmetric the asymmetry is reproduced, not tidied** — a cleanup here would be a silent permission change on a live system. This is also why there are 8 resources rather than the 4 a mockup suggests: resources are split so each ACTION has a single uniform role set (collapsing `academic_year.edit` with the calendar and section editors would have silently granted or removed `academic_coordinator` access).
- **Grants are NOT in the JWT.** Role still comes from `app_metadata.role` via `getClaims()` (KD #35), but capabilities are a cached DB read tagged `permissions`, so the editor's `revalidateTag('permissions')` makes an edit apply on the next page load — **no re-login**. Had they ridden in the token, an edit would not take effect until the token refreshed.
- **Failure mode is defaults, deliberately neither open nor closed.** Missing table / query error / empty table all fall back to `DEFAULT_ROLE_CAPABILITIES`. Failing open would grant everything; failing closed would lock every role out of the app over a transient error. This fallback is also what made the code **safe to deploy before migration 101 was applied**. Once the table has rows it is **authoritative and is not merged with the defaults** — merging would make a deliberately-revoked capability un-revokable.
- **Two `unstable_cache` traps already paid for elsewhere are obeyed here:** the **service** client, never a cookie-scoped one (KD #54), and **arrays, never Sets**, since it JSON-serialises (KD #153).
- **First real consumer — one document-validation queue for both sides of enrolment.** The route now picks the capability from the student's enrolment state rather than the caller's role name: `enrolled ? 'documents_post_enrolment.validate' : 'documents_pre_enrolment.validate'`. KD #147's Lock #2 is intact — it is now expressed as a capability the enrolment state selects, so one person can hold both sides. Also capability-gated in the same batch: AY setup, calendar, classes, subjects, staff, subject weights, and grade-change approval (which stopped being "is this role named `school_admin`" and became a capability — cross-ref KD #41's approver pool).
- **`/account` was made reachable for every role** in the same batch (it had been gated such that some roles could not open their own account page).

Every current holder has all three, so nothing moves today — but revoking one in `/sis/admin/roles` now hides exactly the controls it should. The dashboard's `isOfficer` became `documents_post_enrolment.chase`, which is what every one of its gated elements (priority panel, chase strip, act-now callout, bulk-remind footer) ends up calling.

**Standing rule: when a page moves onto the capability layer, the thing that links to it moves with it.** Four link sources, one mechanism, one test.

### KD #174

**The link rule extends to hrefs written inside a page** (2026-08-01; no migration). KD #173 closed the four _systemic_ link sources — nav, quick-actions, to-dos, ⌘K. It could not see a plain `<Link href="/records/students/…">` typed into a component, and that is where the next instance was: the Classroom roster rendered **every student name** as a link to the permanent record, which is registrar-and-above. A form adviser clicking a student on their own roster was proxy-bounced to `/`. Found during the 2026-07-31 academics-training triage, live throughout the Term 3 parallel run.

**Four teacher-reachable sites, found by classifying all ~35 `/records/students/` call sites** rather than fixing the reported one: `classroom-roster-table.tsx`, `classroom-health.tsx` (the Overview at-risk panel), `classroom/[sectionId]/write-ups/page.tsx` (adviser-only, so **every** FCA hit it), and `markbook/sections/[id]/attendance`. The other ~31 are exempt — under `/records`, `/admissions`, `/sis`, `/p-files`, or inside `canSeeAdmin`-gated blocks — and the exempt list is part of the record, not a footnote. One exemption is _accidental_ and worth watching: `components/sis/command-palette.tsx` lists `teacher` in `STUDENT_SEARCH_ROLES` while `/api/sis/search` `requireRole`-403s them, so the item never renders — it becomes a dead link the moment that API widens.

**Mechanism.** New predicate `canOpenStudentRecord` in `lib/classroom/scope.ts` (true for `oversight` only — defensible because `OVERSIGHT_ROLES` and the `/records` rule name the same three roles, and `__tests__/classroom/student-record-link.test.ts` pins that equality in both directions). New `components/ui/student-record-link.tsx` takes a **required** `canOpen` — no default, so a forgotten decision is a build error rather than a silently hidden link; do NOT push the prop into `IdentifierLink`, whose ~30 call sites are nearly all registrar-only. The wrapper owns the URL, which is what lets `__tests__/auth/module-inpage-link-reachability.test.ts` assert that no classroom file contains a `/records` literal at all.

**That guard is deliberately bounded, and says so in its header.** It walks `app/(classroom)` + `components/classroom`, collects static href prefixes via the TS compiler API, and checks `isRouteAllowed` for every role that can open the module. It cannot see links inside shared components, and cannot resolve `{canX && <Link/>}` without dataflow analysis. A fully general in-page-link guard is **not feasible** — KD #159 and KD #173 get their leverage from one guard per route, which in-page links do not have. Extend module by module, deliberately.

**The fourth site was retired, not guarded.** `app/(markbook)/markbook/sections/[id]/attendance` had **no session or role check of any kind** (only `if (!section) notFound()`) under the teacher-admitting `/markbook` prefix. Its parent became a redirect stub to `/classroom/[id]` when the Classroom module superseded it (KD #160, Phase 7) and this sub-route was simply missed. Redirecting it removes an unguarded surface instead of bolting a guard onto UI nothing links to. One deliberate tightening: a subject teacher who could previously open it and see empty rows now gets a 404, matching `is_adviser_for_section`. Two now-dead files were deleted with it (`markbook/sections/[id]/roster-table.tsx`, `components/markbook/attendance-readonly-table.tsx`).

### KD #175

**The SECURITY DEFINER lockdown missed one, and it was the one that deletes marks** (2026-08-01; migration 107). KD #167 revoked seven definer RPCs from `public`/`anon`/`authenticated` across migrations 103 and 104. **`sync_grading_sheets_from_config` (migration 052) is in neither list.** Found while writing 107 for unrelated reasons, by cross-checking every definer RPC the app calls against both revoke lists.

Per 104's own analysis, Supabase grants EXECUTE on `public` functions to `anon` and `authenticated` **directly**, so the omission meant it was callable through PostgREST by any anon-key holder — and `SECURITY DEFINER` bypasses both RLS and migration 004's blanket write denial. This is not a read: the function **truncates** `grade_entries.ww_scores`/`pt_scores` via `[1:v_max_slots]`, so a caller supplying a `subject_config` id destroys entered marks across every unlocked sheet for that subject. It needs a uuid it cannot guess, but config ids appear in admin URLs and API responses.

Migration 107 revokes it naming `anon` explicitly — the omission that made 103 ineffective on its own — and re-grants to `service_role`. **Verified live after applying:** anon call returns `42501 permission denied`, not an execution error. The other two definer-adjacent RPCs the app calls (`apply_change_request_atomic`, `transfer_student_section`) are **not** `SECURITY DEFINER`, so RLS still covers them; this was the only gap. `CREATE OR REPLACE` preserves privileges, so any future migration replacing this function must re-assert the revoke — 108 does.

### KD #183

**Two failure modes get guardrails rather than fixes: silent truncation, and a failure that reads as good news** (2026-08-10; no migration). Prompted by three bugs in one afternoon that shared a root — code written against what was true that day, or what a column's name implied, rather than against what the system actually does.

**The measurement is the decision.** Three parallel audit agents proposed six HIGH findings. Counting each against production removed half of them: `findTruncationBlockers` was estimated at 2,940 rows and is **168** (the estimate read locked sheets; only 32 unlocked sheets exist school-wide), `sheet-impact` 960–1,440 → **620**, the AY-wide `section_students` reads up to 840 → **405**. Acting on that report unreviewed would have spent Phase 1 on three non-bugs while the real ones waited. **A plausible estimate is the failure mode here, not the evidence.**

**Four defects were live and are fixed:**

1. **A registrar could not save a profile or family record.** Every mobile column on the admissions tables is numeric (`motherMobile` a `number` on 498/498 AY2026 rows), the row was cast to a type promising `string | null`, and both edit sheets submit the whole form — so an untouched phone went back as a number and zod 400'd the entire payload. Fixed at both ends: `normaliseApplicationRow` coerces at the one read boundary, and the phone/postal validators accept a number. The comment claiming reads already coerced described a fix nobody had written — **a comment asserting an invariant is not the invariant**.
2. **The attendance register printed short.** 1,610 rows against a 1,000 cap, so the official `.xlsx` was missing about a third of a term and looked complete.
3. **Leave quotas undercounted from ~T2.** The compassionate tally reads AY-wide with no term filter: 5,925 rows, nearly 6× the cap.
4. **The compliance audit export stopped at 1,000.** 1,322 rows in the last 90 days.

**Six silent failures fixed**, all of the shape _a broken query renders as reassurance_: the report-card comment hard gate could pass vacuously (`cumulativeCommentGaps` re-read the roster and discarded the error — it now takes the caller's, so the second read is gone rather than guarded); the adviser at-risk list read "nobody is at risk"; class-assignment readiness read "every student has a class"; the Markbook teacher panel returned `severity: 'good'`; the change-request badge folded an error into the same zero as "none pending"; and `lib/home/todos.ts` gathered with `Promise.all`, so one broken source blanked the panel — `allSettled` now, with the failing source named in the log.

**The guardrail is the durable part.** `__tests__/data/no-unpaginated-high-volume-reads.test.ts` scans for reads of tables that grow, and **every allowlist entry must carry a row count measured in production with the date it was counted**. Two rules keep it from decaying into the thing it replaced: an entry claiming ≥900 rows is treated as an unfixed bug rather than an exemption, and a stale entry fails. Writing it surfaced three more unpaged `audit_log` reads — that table grows with nothing but time — and one table name I had invented from a guess (`report_card_comments` does not exist; the API 404s).

⚠ **Still open, and it needs a design decision rather than code.** Five queue loaders feeding `lib/home/todos.ts` (`unsynced-students`, both `document-validation`s, `levels-awaiting-sections`, the admissions chase) still return `[]` on failure by deliberate, documented choice. On a badge that is indistinguishable from "nothing outstanding". The fix is a result shape that separates _confirmed empty_ from _fetch failed_ and a UI that can show a degraded state — what that looks like on a badge is the school's call, not a refactor.

### KD #184

**Relief teachers: a substitute works a class without the regular teacher's name coming off anything** (2026-08-12, rebuilt 2026-08-13; migrations 112–118). A teacher goes on leave, somebody stands in, and later the teacher comes back. Before this the only way to record that was delete the assignment and create a new one — which rewrites history, because every "who owns this" in the app is resolved live from `teacher_assignments` at render time and nothing is persisted. Deleting a form adviser mid-year silently reprints an already-published T1 report card under the replacement's name.

**Cover is ONE NULLABLE COLUMN — `teacher_assignments.relief_teacher_user_id`.** Set it and the substitute gets the class; clear it and they lose it. Nothing else.

**This reverses the first build, and the reversal is the part worth keeping.** Migrations 112–116 made cover a table: a start date, an end date, a reason, notes, who arranged it, who ended it, a partial unique index, a `SECURITY DEFINER` window helper, and four migrations of corrections on top. All of it served a requirement nobody asked for — that cover keep its own history. `audit_log` already had that, and it is the only history anyone wanted. The date window was worse than surplus: it was a **second source of truth about who may act on a class**, and 115 exists solely because the SQL and the app disagreed about it. Mr Ace's account of the feature was one sentence — _"a subject teacher or FCA will just be added a relief teacher to them, it's like an enable and disable button"_ — and everything past that sentence was invented. **The general lesson: a requirement you cannot attribute to the person asking is one you made up.**

What the column cannot express, and why that is fine: scheduled cover ("starts Monday") — arrange it on Monday; a list of past covers — `audit_log`; a reason code — also `audit_log`, and nothing ever read it back. What it expresses _better_: "a teacher cannot cover their own class" was a route check under 112 because it compared two tables; on one row it is a CHECK constraint.

**Not a third `role` value** — that part of the original reasoning stands. A third role would have failed both CHECK constraints on the table, carried no uniqueness (both indexes are `where role = '...'` partials), fallen through both arms of `lib/classroom/scope.ts`, and been duplicated on every rollover by `copy_teacher_assignments`. (017 names its columns explicitly, so the column does **not** roll into a new year — cover is a fact about this term.)

**The split this forces, and it is the whole decision.** One question became two with different answers:

- **who may ACT here** — substantive teacher **plus** anyone covering. Attendance, marks, roster, change requests.
- **who IS here** — substantive teacher only. Write-ups and the report card comment, which the regular adviser writes even while away (Mr Ace, 2026-08-11); and the "is the post filled" coverage checks, which a relief must not satisfy or an unstaffed section would publish.

`loadClassroomAccess` returns both (`capability` / `substantiveCapability`). Which predicate takes which is not left to reviewers noticing: `__tests__/auth/assignment-read-classification.test.ts` classifies every one of the ~59 files that read assignments and fails the build on a new unclassified one. Getting it backwards prints the wrong teacher on a report card, and `evaluation_writeups` has **no adviser predicate in RLS at all** (migration 018 admits any authenticated role), so five application sites are the only thing enforcing it — there is no database backstop.

**One trap worth keeping from the first build.** A policy helper is **not** an RPC: 114 revoked `EXECUTE` on `has_active_relief_for_assignment` from `authenticated`, copying the lock-down pattern of 103/104 — but RLS policies run as the querying role, so every cookie-scoped read of `teacher_assignments` returned "permission denied" and the section Teachers tab went blank while the service-client staff directory showed the same rows correctly (fixed in 116). 117 removes the helper entirely: cover is a column on the row the policy already has, so the test is a comparison and that whole class of failure is gone.

**Arranged on the class row, both ways round.** The switch is `PATCH /api/teacher-assignments/[id]` and it appears in two places, because "who is covering?" is asked from two ends: on `/sis/admin/staff/[teacherId]`, where each of a teacher's classes is a row (the morning-someone-calls-in-sick flow — one person, five decisions), and on a class's own Teachers tab. There is no Cover page and no page-level button that then has to ask which class it meant. `staff.manage_relief` is school admin and above, deliberately narrower than the `staff.edit_assignments` beside it, which the academic coordinator holds.

**The substitute is validated against `getTeacherList()`, never `getStaffDisplayNameById()`.** The latter returns every auth user with an email — the ~1,000 parent portal accounts included. There is no FK across schemas, so this route is the only check, and a parent uuid in that column would be handed RLS read on the class's students, grading sheets and attendance. Disabled accounts are excluded here and admitted by the sibling create route, on purpose: there the question is "whose class is this?" (a teacher on long leave is still the name on the report card), here it is "who is taking the lesson?" (a disabled account cannot sign in to take the register).

**Verified on prod (2026-08-13).** `scripts/verify-relief-migrations.ts` is read-only and safe to run against production; it passes 7/7. Its own header states that a **service-role check cannot see RLS** — which is the whole reason the 114 failure above went unnoticed until a cookie-scoped read hit it. Mr Ace then confirmed in a browser that a teacher can mark their own sheet, that adding a relief opens the cells for the substitute, and that clearing it closes them again.

### KD #185

**One subject teacher per (section, subject)** (2026-08-13; migration 118). Migration 003's header stated this rule in words — _"subject_teacher — one per (section, subject) pair"_ — and then created an index on `(teacher_user_id, section_id, subject_id)`, which only stops the **same** teacher being listed twice. Two different teachers could both hold one class's Filipino, and did. Open since 003; found by Mr Ace reading the section Teachers tab.

**Why the stated rule is the right one:** a grading sheet resolves its subject teacher live from this table (KD #158) and has room for one name. With two rows the sheet, the masterfile and the report card each answer "whose class is this" by whatever order the rows came back in. The adviser rule was always correct — `teacher_assignments_form_adviser_unique` is on `(section_id)` alone — and 118 makes the subject rule its exact counterpart.

**The migration aborts rather than de-duplicating.** Which of two teachers to remove is a staffing decision; the wrong one removed takes access away from someone actually teaching. So it names the doubled-up classes and stops. Enforced in three places, deliberately: the index, a pre-flight check in the bulk schema (a batch is one statement, so an index failure would lose 200 rows of work to a message that does not say which two lines clashed), and the Assign dialog, which no longer offers a subject that already has a teacher, or the adviser role when the class already has one.

**A lesson about reading a schema:** the index and the comment three lines above it disagreed, and I took the index as the intent and wrote "co-teaching is deliberate" into a plan. When a constraint contradicts its own stated purpose, that is a bug in the constraint, not an undocumented feature.

**Fixed in passing, pre-existing:** a teacher may advise several sections — the unique index is on `(section_id)` alone — but the staff drawer `.find()`-ed the first adviser row and its change path deleted whichever id it held, stranding the other class with no adviser and nothing on screen saying so.
