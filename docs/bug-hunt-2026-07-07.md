# HFSE SIS — Bug hunt findings & fix plan

## Context

You asked for an exhaustive, adversarially-verified sweep of the codebase for real bugs, perf issues, cleanup targets, UI defects, and docs misalignments. This was run as a multi-agent workflow: 13 scoped finder agents (per-module bug hunts + perf + cleanup + UI/design-system + docs-alignment + a dedicated pass on the uncommitted working-tree diff) plus 3 coverage-gap finders, producing 59 raw findings (43 after removing exact duplicates).

The workflow's automated adversarial-verification stage repeatedly died on the session token limit (reset time was ~4.5 hours out), so instead of re-queuing it against an exhausted budget, I hand-verified a representative sample across every severity tier directly against the code (Read/Grep, no edits). Result: **8 of 9 sampled findings held up** (one was actually _worse_ than reported), and **1 was a hallucination** (a claimed `px-6!` in `card.tsx` — the real code just has `px-6`, confirmed via `git diff` and direct read; dropped). That hit rate is why the rest of the list below is presented as "finder-reported, high specificity, not all individually re-run by me" rather than "100% independently confirmed" — treat items marked **[verified]** as solid, and give the others a quick look before acting, especially before touching anything security-sensitive.

Two exact-duplicate clusters were collapsed: three "dead compare-mode loader" findings (admissions/attendance/records) became one, and two identical `oklch()` findings (reported by two different finders) became one.

## How to use this

This is a fix backlog, not a single task — pick items top-down by severity, or hand a batch to subagents. Each item names the file, the concrete failure, and a fix direction. I did not write any code; nothing here has been changed yet.

## CRITICAL — fix first

### C1. Parent-facing report-card API leaks unpublished grades/comments + wrongly 403s withdrawn students **[verified]**

**File:** `app/api/parent/v2/report-card/route.ts:116-176`

Two compounding bugs in one route (external, Bearer-token-authenticated, consumed by the admissions portal SPA):

1. When the client omits `termNumber`, the publication-window check (`pubQuery`, lines 131-140) only requires that **one** term has an active window anywhere on the section. `buildReportCard` then returns **all four terms'** grades, attendance, and FCA comments unfiltered (the per-term filter at lines 166-176 only runs `if (termNumber !== null)`). A parent (or anyone with a valid Bearer token) who calls the endpoint without `termNumber` gets unpublished, unlocked, draft data the registrar never approved for release.
2. The enrolment lookup (`.not('enrollment_status','in','("withdrawn")')`, line 120) excludes withdrawn students entirely, contradicting KD #150's explicit decision that the parent portal **includes** withdrawn students (gated only by the publication window). It also arbitrarily picks one enrolment via `.limit(1).single()` with no ordering, so a student with historic + current rows can have the wrong section's window checked.

**Fix:** When `termNumber` is omitted, fetch **all** currently-active publication windows for the section, derive the published term set, and filter the payload to exactly that set (never "any one window unlocks everything"). Drop the withdrawn-exclusion filter on the enrolment lookup — fetch all `section_students` rows for the student and check publication windows against all their section_ids, matching what the sibling `/api/parent/v2/students` route already does correctly.

### C2. PostgREST ILIKE filter injection in parent→student authorization **[verified]**

**File:** `lib/supabase/admissions.ts:253`

`getStudentsByParentEmail` splices the caller's own account email straight into a PostgREST `.or()` ILIKE filter with zero escaping: `.or(\`motherEmail.ilike.${trimmed},fatherEmail.ilike.${trimmed}\`)`. This is the **sole authorization basis** for both parent v2 endpoints (student listing + report-card fetch). `%`and`\_`are ILIKE wildcards and PostgREST additionally maps`\*`→`%`. Supabase/GoTrue allows these characters in email local-parts, so an attacker who registers e.g. `%@gmail.com` matches every parent with a Gmail address and can pull any of those children's full report cards. Benign collisions are also plausible (`john_smith@...`matches`johnXsmith@...`).

**Fix:** Escape `%`, `_`, and `*` before interpolating (`trimmed.replace(/([\\%_])/g, '\\$1').replace(/\*/g, '\\*')`), and reject emails containing `,`/`(`/`)` outright since they break the `.or()` condition-list syntax. Better: run two separate `.ilike('motherEmail', escaped)` / `.ilike('fatherEmail', escaped)` queries and union client-side, removing the string-splicing entirely.

### C3. Masterfile grade export silently truncates at the PostgREST 1000-row cap **[verified]**

**File:** `lib/markbook/masterfile.ts:473-485`

`loadMasterfile`'s `grade_entries` read has no `.range()`/`fetchAllPages` — confirmed via grep that this file is absent from the 19 files that do use `fetchAllPages`, while sibling files `lib/markbook/dashboard.ts` and `lib/markbook/drill.ts` (which read the same table at the same scale) both use it. A level of even ~20 students × 13 subjects × 4 terms already exceeds 1,000 grade-entry rows; a typical HFSE level (40-100 students) yields 2,000-5,200. This payload feeds both the on-screen Academic Summary dashboard **and** the official `.xlsx`/`.csv` report-book export — the school's official consolidated academic record silently drops most grade cells, and derived award tiers (KD #95) computed from the truncated data are wrong.

**Fix:** Wrap the `grade_entries` read in `fetchAllPages` from `lib/supabase/paginate.ts`, exactly as `lib/markbook/dashboard.ts`/`drill.ts` already do. Same file's `attendance_records` read (line ~503) should get the same audit as roster size grows.

## HIGH

### H1. Evaluation write-up PATCH lets any form adviser write/submit FCA comments for any student school-wide **[verified]**

**File:** `app/api/evaluation/writeups/route.ts:50-64`

The teacher gate checks only that the caller is form adviser of the request body's `sectionId` — it never checks that the request body's `studentId` actually belongs to that section's roster. A teacher who advises any one section can pass their own valid `sectionId` plus an arbitrary `studentId` (visible elsewhere in the UI) and create/overwrite/empty/submit/un-submit that student's FCA write-up. Since write-up content renders on the report card (KD #49) and roster-based submitted-counts key by `student_id` (KD #120), a forged row can also satisfy the KD #129 comment hard-gate for a section the caller doesn't advise.

**Fix:** After the adviser gate (`auth.role === 'teacher'`), query `section_students` for a row matching `(section_id=sectionId, student_id=studentId, enrollment_status != 'withdrawn')` and 403/422 if absent. Consider deriving `sectionId` server-side from the student's current active enrolment instead of trusting the body.

### H2. Locked-sheet change-request "apply" writes the client's entire score array, not just the approved slot **[verified]**

**File:** `app/api/grading-sheets/[id]/entries/[entryId]/route.ts:214-235, 606-632`

`buildEntryPatch` (line 620) does `patch.ww_scores = body.ww_scores` — the **whole array** the client currently has in browser state — even though the approval check (`valuesMatch`, lines 214-235) only validates the single approved `slot_index`'s value. If another registrar applies an unrelated correction to the same entry while this registrar's browser still holds stale scores for other slots, applying the approved request silently reverts those other slots — and the audit trail (`buildAuditRows`) attributes the reversion to an `approval_reference` that never covered it. This is exactly the kind of unapproved-locked-sheet-edit Hard Rule #5 exists to prevent.

**Fix:** Build the patch server-side from a freshly-read entry: take the current `ww_scores`/`pt_scores` array from the DB, replace only `slot_index` with the approved value, and pass that (not the client's array) to `apply_change_request_atomic`.

### H3. `annual-letter` route selects columns that don't exist — the T4 non-examinable letter can never be saved **[verified]**

**File:** `app/api/grading-sheets/[id]/entries/[entryId]/annual-letter/route.ts:65-66`

Selects `subjects.subject_code` and `sections.section_name`. Verified against the schema (`supabase/migrations/001_initial_schema.sql:51-102`): the real columns are `subjects.code` and `sections.name`. Neither alternate name exists anywhere in 76 migrations. PostgREST errors on an unknown embedded-select column, so `sheetRes.error` is always set and the route 404s on every call — the registrar can never set/change `annual_letter_grade` (KD #100) via `<AnnualLetterInput>`, and the T4 `nonexam_finals_missing` publish-readiness gap can never be cleared through the UI.

**Fix:** Change the select to `subject:subjects(is_examinable, code)` / `section:sections(academic_year_id, name)` and update the downstream field reads accordingly. Add a route test that would have caught this.

### H4. Two applications-dashboard "needs follow-up" counts don't match their own deep-links, and are worse on real (unstamped) data

**Files:** `app/(admissions)/admissions/page.tsx:498`, `components/sis/student-data-table.tsx:350-356`

The insight's count (`getOutdatedApplications`) deliberately keeps NULL-`applicationUpdatedDate` rows ("never updated = most urgent"), but the deep-link filters to `staleness=Warning,Critical` — which excludes the "Never updated" tier — and the destination table further server-filters to active funnel stages. Separately, the on-screen Staleness column computes tiers from the raw (unfallback'd) `applicationUpdatedDate`, while the dashboard count uses `applicationUpdatedDate ?? created_at`. Per project notes, `applicationUpdatedDate` is ~0/490 populated in production — so in prod, essentially every row reads "Never updated" in the table (which the follow-up link excludes) while the dashboard count (using the `created_at` fallback) is large and non-zero. Net effect: the insight fires with a big number, the deep-link opens to an empty or near-empty table. Violates the project's own KD #124 "count == drill" rule and defeats KD #149's "single entry point" design. This is invisible on the AY9999 seed because the seeder stamps the column.

**Fix:** Make one predicate the source of truth for both. Either (a) add "Never updated" to `STALENESS_FOLLOW_UP_VALUES` and to the table's tier computation (apply the same `applicationUpdatedDate ?? created_at` fallback in `student-data-table.tsx`), or (b) scope the dashboard count to exactly what the destination table can show. Given production has zero stamped dates today, fixing the fallback (a) is probably the higher-leverage change.

### H5. Bulk auto-sync re-fetches the entire levels+sections tables once per student, sequentially

**File:** `app/api/sis/students/auto-sync/route.ts:49-55`, `lib/sync/students.ts:445-458`

The "sync all unsynced enrolled students" admin action loops sequentially and awaits `syncOneStudent` per row; each call re-fetches the full `levels` table and the full AY `sections` list, which are identical across every student in the run. For a fresh-AY backfill (the exact scenario this queue exists for, KD #90) of dozens-to-~500 students, that's O(N) redundant full-table reads with zero parallelism — slow, and a serverless timeout risk on a large queue.

**Fix:** Hoist the AY-invariant reads (levels, sections) out of `syncOneStudent` into the bulk route, fetch once, pass the snapshot down; process candidates with bounded concurrency instead of a fully sequential loop.

### H6. Evaluation dashboard/drill fetch all AY write-ups with no pagination — same 1000-row cap as C3 **[verified via the same grep as C3]**

**Files:** `lib/evaluation/dashboard.ts:94-99`, `lib/evaluation/drill.ts:248-253`

Both files are absent from the `fetchAllPages` consumer list (confirmed by the same grep used for C3). ~490 enrolled students × 3 terms (T1-T3) of write-ups ≈ 1,470 rows — once that threshold is crossed, submission %, the submitted count, the velocity sparkline, and the submission-status drill all silently undercount by whatever the DB happens to truncate.

**Fix:** Wrap both fetches in `fetchAllPages`, same pattern as `lib/sis/records-insights.ts`.

### H7. 07-api-routes.md documents entire route families — and a PDF microservice — that don't exist

**File:** `docs/context/07-api-routes.md:63,104-112,119,128-145`

Verified against the filesystem: no `app/api/comments`, no `app/api/config`, no `/api/report-card/[studentId]/pdf`, no `/api/compute/overall`; attendance routes are `/api/attendance/daily` + `/api/attendance/[sectionId]`, not the documented `/api/attendance/:termId/:sectionId`. The doc also describes a separate FastAPI "PDF Microservice" that directly contradicts KD #7 and `tech-stack.md`'s "PDF generation deferred — browser Print covers current volume," and uses the retired `admin` role throughout (KD #39 retired it).

**Fix:** Rewrite against the current `app/api` tree; drop the Comments/Config/PDF-microservice sections and the phantom routes; replace `admin` with `school_admin`.

### H8. `oklch()` hardcoded color violates Hard Rule #7 (reported twice, same finding)

**File:** `components/shared/document-completeness-table.tsx:947`

`shadow-[0_-4px_6px_-2px_oklch(0_0_0/0.04)]` — the only `oklch(...)` occurrence in `app/`/`components/` outside `globals.css`. Every other inline shadow in the codebase uses the established `rgba(...)` convention.

**Fix:** Replace with `shadow-[0_-4px_6px_-2px_rgba(0,0,0,0.04)]` or a named shadow token in `globals.css` if this shadow shape is needed elsewhere.

### H9. `resolveStatus` has no branch for a stored `'Expired'` document status

**File:** `lib/p-files/document-config.ts:224-253`

Handles `rejected`/`to follow`/`uploaded`/`valid` explicitly and derives `expired` only from `expiry < today`. A raw stored `'Expired'` status (which `freshen-document-statuses.ts` writes when `expiry <= today`, i.e. inclusive) falls through to `return 'missing'` whenever the date check doesn't independently fire — e.g. on the expiry day itself, or after a date correction without a status reset. The student then lands in the wrong chase bucket ("missing" instead of "needs renewal") and completeness counters are wrong for that slot.

**Fix:** Add `if (s === 'expired') return 'expired';` before the derived-date check, keeping the date check as a backstop for stale `'Valid'` rows.

### H10. Non-examinable "Awaiting STP completion" bucket is permanently wrong — reads columns dropped by migration 050 (KD #96)

**File:** `lib/sis/process.ts:947-953` vs `lib/sis/queries.ts:767-867`

Iterates `STP_STATUS_COLS` (icaPhotoStatus, financialSupportDocsStatus, vaccinationInformationStatus) against a documents row whose `docColumns` (built from `DOCUMENT_SLOTS`) no longer includes those 3 slots — they were removed in migration 050 per KD #96. Every lookup reads `undefined`, `(undefined ?? '').trim() !== 'Valid'` is always true, so the "Awaiting STP completion" count on the SIS hub's lifecycle card equals the total STP-applicant count forever, regardless of actual ICA progress.

**Fix:** Rewrite the predicate to read `stpApplicationStatus` (already fetched per KD #61): incomplete when `stpApplicationType` is set and `stpApplicationStatus` is not `Approved`/`Rejected`. Delete `STP_STATUS_COLS` and the dead docs-row branch.

## MEDIUM

Grouped by area; each is independently actionable. File:line and the concrete failure are in the raw findings — summarized here for triage:

- **`lib/p-files/freshen-document-statuses.ts:98-101`** — expire (`<= today`) and revive (`>= today`) both match the expiry date itself, so a document expiring _today_ can oscillate Valid↔Expired across runs, polluting the audit log and flickering the chase queue for one day. Fix: make revive strictly `.gt(today)`.
- **`lib/evaluation/dashboard.ts:139`** — submission KPI counts submitted-but-empty write-ups and withdrawn students' write-ups, disagreeing with the "Outstanding write-ups" chase card on the same dashboard (which correctly applies KD #120's submitted-AND-non-empty + roster rule). Fix: apply the same predicate used in `getWriteupProgressByTerm`/`loadChaseStateUncached`.
- **Export sheet ignores the active "mine" scope** (`components/ui/data-table/export-sheet.tsx`) — the CSV preview/export applies statusTab+facets+search but not the `meScope` toggle the on-screen tab counts use, so an export can be silently narrower than what the visible toggle promises. Fix: thread `meScope`/`mineActive` into the export seed.
- **Export sheet can't show or clear grouped-facet (`facetGroups`, KD #152) selections** (`components/ui/data-table/index.tsx:619`) — the sheet only receives the top-level `facets` prop, not the flattened `facetGroups`, so a Stage-filter selection on `/admissions/applications` silently narrows the export with no visible chip or way to clear it. Fix: pass `[...facets, ...facetGroups.flatMap(g => g.facets)]`.
- **Export sheet raw-columns race** (`components/ui/data-table/export-sheet.tsx:312`) — a source still `'loading'` when filters change is never marked stale, so it can resolve and overwrite as `'loaded'` keyed to the old row set, exporting blank cells for newly-matched rows with no warning. Fix: track a scope epoch; discard/mark-stale results from a stale epoch.
- **URL-state pagination gets silently dropped by the debounced search-write** (`components/ui/data-table/index.tsx:271`, `use-url-state.ts`) — the debounced snapshot omits page/pageSize, so 300ms after any search keystroke (or on mount) `?ns.page=`/`?ns.pageSize=` get deleted from the URL, defeating the KD #84 "page survives refresh/share" contract. Related: a non-debounced write doesn't cancel a pending debounced one, so a facet click right after typing can get clobbered by the stale debounced write 300ms later. Fix: include page/pageSize in the debounced snapshot; clear any pending timer in the non-debounced write path.
- **`generate-index-button`/publish-readiness style gaps**: T4 publish-readiness "grades missing" check (`lib/markbook/publish-readiness.ts:414-431`) doesn't apply KD #148's enrolment-coverage N.A. logic, so late enrollees get falsely flagged at T4 publish for terms the report card correctly renders as N.A. Fix: reuse `lib/report-card/enrolment-coverage.ts`.
- **`lib/markbook/grade-diff.ts:24-28`** — the Alerts (±5 significant-change) column loses prior-term history across a mid-year section transfer (KD #67) because prior grades are keyed by the old `section_student_id`. Fix: resolve by `student_id` across all of the student's AY enrolments, like `build-report-card.ts` does.
- **`components/grading/score-entry-grid.tsx:326-390`** — a rejected/cancelled score edit doesn't revert the optimistic local state, so the cell (and its Total) can display a value that was never actually saved until a page refresh. Fix: snapshot-and-restore on error/cancel.
- **`lib/sis/process.ts:393-396`** — the lifecycle timeline's "Withdrawn on {date}/{reason}" for an enrolled-then-withdrawn student (KD #150) still reads the application-stage fields, not `section_students.withdrawal_date`/`withdrawal_reason`, so it shows the enrolment date/remark instead of the actual withdrawal. Fix: select the withdrawal columns and prefer them when the withdrawal is post-enrolment.
- **`lib/sis/queries.ts:1074-1104`** — cross-AY student search breaks on a comma or parenthesis in the query (PostgREST `.or()` metacharacters), silently returning "no matches" for names like "Tan, Wei Ming". Fix: quote/escape operands or run per-column queries and union.
- **`lib/attendance/drill.ts:563-588`, `queries.ts:370-393`** — the compassionate/vacation quota drill and the per-student monthly attendance % both under/over-count relative to their own AY-wide siblings (the drill drops pre-transfer usage on withdrawn rows; the monthly breakdown double-counts school days when audience-specific calendar overrides exist). Fix directions are in the raw findings; both have a correct sibling implementation to copy from (`getCompassionateUsageForSection`, the dashboard's `audience='all'` filter).
- **`lib/markbook/publish-readiness.ts:327-336`** — the T4 grade_entries read spans all 4 terms for a full section (~2,080 rows for 40 students × 13 subjects) with no pagination — same class of bug as C3/H6 but soft-gated so lower severity.
- **`components/sis/student-data-table.tsx:314-322`** — the new Pipeline-strip column has no accessor and no `excludeFromExport` meta, so it exports as a blank "Pipeline" column in every admissions CSV; the 9 hidden `stage_*` facet columns also clutter the export column-picker. Fix: add `meta: { excludeFromExport: true }`.
- **Dead code, safe to delete** (verified structure, not re-run individually): `lib/admissions/compare.ts`, `lib/attendance/compare.ts`, `lib/sis/records-compare.ts` (all three superseded by Module Insights, KD #140-143, zero importers) — collapse the duplicate reports into one cleanup task; plus the now-dead `getMarkbookCompareKpis` export in `lib/markbook/compare.ts` (its live siblings `getSubjectPerformanceTrend`/`getSubjectLevelTrend` stay).
- **Docs:** `14-modules-overview.md:158` marks registrar's "Module switcher visible" as `—`, contradicting `allowedModules.length > 1` (registrar has 5+ modules) **[verified]**. `04-database-schema.md:282` still says section index numbers are "immutable once assigned," contradicted by the shipped Generate-class-index feature (KD #136). `project-layout.md:29` says migrations run "001 → 074"; 075 and 076 exist **[verified]**. `09-design-system.md`'s "currently installed primitives" table is missing ~19 real primitives (Dialog, AlertDialog, Popover, Command, Switch, etc.).
