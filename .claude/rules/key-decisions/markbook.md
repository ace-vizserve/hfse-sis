They are now **signed, single-effect action links** that decide from the email without a login. **Token** (`lib/change-requests/action-token.ts`, server-only, no DB): a stateless HMAC-SHA256 over `{ requestId, action, approverId }` (base64url payload `.` sig, `timingSafeEqual`), keyed on new server-only env `CHANGE_REQUEST_ACTION_SECRET` (≥32 chars, per-env; rotating invalidates outstanding quick-links; if unset → buttons gracefully degrade to the old deep-links + a build-time warn from `lib/env.ts`). **No time expiry** — validity is "until the request is decided" (single-effect: once it leaves an actionable state the token does nothing). **Flow:** per-approver token in the email → `GET /change-requests/act?token=…` renders a **prefetch-safe confirm page** (`app/(action)/change-requests/act/page.tsx`, unauthenticated — added to `proxy.ts` `PUBLIC_PATHS`; GET never mutates) showing the request + one **Confirm** button (reject requires a reason) → `POST /api/change-requests/act` (token-gated, **no `requireRole`**; resolves the approver via `service.auth.admin.getUserById`) runs the decision **as that approver**. **Key refactor:** the decision pipeline was extracted from the PATCH handler into **`lib/change-requests/decide.ts`** (`decideChangeRequest({ actingUser, action, decisionNote, via })`), shared by the in-app `PATCH /api/change-requests/[id]` (unchanged behavior, still `requireRole`-gated) and the token route — so all guards behave identically (designated-approver check, role gate, status guards, primary-flips-status vs **secondary co-sign** (which works from email too), same-person guard, optimistic `.eq('status', expectedStatus)`, reject-needs-reason, audit, notify). Audit context gains `via: 'in_app' | 'email_token'`. Label/recipient helpers (`fetchLabels`, `fetchRegistrarEmails`, `fetchApproverEmails`) moved to `lib/change-requests/labels.ts` to avoid a `lib`←`app/api` import. All edge cases resolve by re-running `decideChangeRequest` against live state at click time. No migration.

### KD #139

Publish-anyway **override tracking** + empty-card **hard blocks** (Sprint 59, 2026-06-09; migration 073). Amends KD #28/#129/#138 (does not reverse them). The registrar's framing: report cards are serious, but incomplete data is **often legitimate** (esp. late enrollees — earlier terms are genuinely blank), so the model is **warn → allow → record the override**, not hard-block everything. (An all-hard-gate + superadmin-break-glass design was explored and **rejected** in favour of this.) **(1) Shared evaluator** `lib/markbook/publish-readiness.ts::computePublishReadiness(service, sectionId, termId)` — the entire computation formerly inline in the `publish-readiness` GET route was moved here (single source of truth, like `cumulativeCommentGaps`); the GET route is now a thin wrapper. These are now hard blockers ("no card," not "incomplete data"). **(3) Override tracking:** `POST /api/report-card-publications` calls the evaluator; any hard blocker → **422 `{ code:'publish_blocked', hardBlockers }`** (replaces the comment-only `comments_incomplete` block — that code is now one hard blocker among the three). A clean publish writes `published_with_gaps = null`; a "publish anyway" past soft gaps writes a snapshot **`published_with_gaps = { gaps, by, at }`** (migration 073 — nullable `jsonb` on `report_card_publications`; **null = clean**) + audit context `overridden:true` + `gaps` (codes). The override is **accountability only — NOT shown to parents**; the publish-window-panel surfaces a "Published with gaps: …" note on such a window (the GET list select now includes the column). **(4) Soft model unchanged:** grades/attendance/sheets-locked/letterhead stay overridable ("Publish anyway"); comments+virtue stay hard. **No superadmin break-glass** (only needed for an all-hard gate, which we didn't build). Bulk dialog `classify()` keys off `hardBlockers`/`softGaps` (blocked includes the new existence blockers); the 422 skip-detection moved to `code:'publish_blocked'`.
