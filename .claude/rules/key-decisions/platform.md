### KD #32

Dates: ISO 8601 UTC in storage/transit; local formatting at render via `toLocaleString('en-SG')`. No `dayjs`/`date-fns`/`moment`.

**SGT calendar-date rule (2026-06-03).** School-calendar values — term windows, attendance dates, `enrollment_date`/`withdrawal_date` — are date-only **Singapore** (UTC+8) dates. Computing "today" as `new Date().toISOString().slice(0, 10)` takes the **UTC** calendar date, which is the _previous_ day during the 00:00–07:59 SGT window — so comparing a UTC "today" against an SGT term window mis-resolves the term at a boundary (e.g. a 7am-SGT enrolment on a term's first day reads as the prior break), and a UTC-sliced display date shows one day off. **Canonical helpers live in `lib/dates.ts`: `sgToday()` (SGT `yyyy-MM-dd`) and `sgDate(iso)` (SGT date of a UTC timestamp).** Use them anywhere a "today" or timestamp→date value is **compared against, or stored as, a school-calendar date** — never raw `.toISOString().slice(0,10)`. Storage/transit timestamps stay full UTC ISO (the rule above is unchanged). Adopted across the term resolver (`getEnrolmentPosition`), section-transfer term-of-date, enrollment/withdrawal date stamps (stage + section-students + sync routes), the attendance writer's today gate, the attendance current-term pages, and the movements feed. `lib/evaluation/ptc-resolver.ts::sgToday` re-exports from `lib/dates` for back-compat. **Deliberately not changed** (cosmetic / not calendar-boundary): dashboard date-range defaults, p-files expiry comparisons, and the seeders. **Update (2026-06-09) — a code audit found two of those weren't actually cosmetic and were switched to `sgToday()`:** the dashboard **term-resolution** source `lib/dashboard/windows.ts` (feeds `resolveCurrentTerm` → every dashboard's "this term" default) + `lib/markbook/dashboard.ts` / `markbook/page.tsx` / `grading/new/page.tsx` (term-by-date), and the p-files **status-write** path `lib/p-files/freshen-document-statuses.ts` (auto-expire/revive on SGT expiry dates) — all mis-resolved/mis-wrote in the 00:00–07:59 SGT window. Genuinely cosmetic display/email date filters (`lib/sis/dashboard.ts` calendar events, `lib/p-files/queries.ts` promise-active, `email-pfile-reminder.ts`) + the seeders stay raw.

### KD #147

Module-ownership & historical-truth-vs-current-truth rule — Admissions ↔ Records ↔ P-Files. Full model in **`docs/context/22-module-ownership-truth-model.md`** (read it before changing any write path touching `ay{YY}_enrolment_{applications,status,documents}` or `public.section_students`). **Principle:** _historical truth_ is append-only, never rewritten (Hard Rule #6); _current truth_ is owned by exactly one module post-enrolment, the others display a **read-only mirror**, and status moves **forward only** (an Enrolled student is never pushed back into the funnel). **Four participants, one shared student record:** (1) **Admissions** owns the application record + pre-enrolment doc validation — **historical/read-only once Enrolled**; (2) **Shared Student Profile** = the `ay{YY}_enrolment_applications` identity row (name/DOB/gender/nationality/address/passport/pass/parents/contacts), **editable from Admissions OR Records** (one record; name also denormalized into `public.students` — keep in sync); (3) **Records** owns the post-enrolment **academic lifecycle** on `section_students` (status/date/section/level/attendance/grades/evaluation/withdrawal/re-enrol) — `applicationStatus` is its mirror, kept in sync by the Records→Admissions cascade; (4) **P-Files** owns the post-enrolment **document lifecycle** (`{slot}Status/Url/Expiry` + append-only `p_file_revisions`/`p_file_outreach`), reads enrollment/profile only. **Two temporal handoffs at enrolment:** academic→Records, documents→Admissions(pre)→P-Files(post). **Enforcement (write-layer):** **Lock #1** — the admissions stage editor (`app/api/sis/students/[enroleeNumber]/stage/[stageKey]/route.ts`) freezes stage-status edits once `applicationStatus==='Enrolled'`, via the shared `isAdmissionsStageFrozen` (`lib/schemas/sis.ts`, also consumed by the enrollment-tab UI so they can't drift). **Exception: `supplies` + `orientation`** happen after enrolment, so they stay editable until **finalized** (supplies `Claimed`/`Cancelled`, orientation `Finished`/`Cancelled`) then lock (422 `stage_finalized`, forward-only); every other stage 422s `enrolled_frozen`. `Enrolled (Conditional)` stays fully editable until it resolves; the withdrawal/re-enrol cascades write via the section-students route, not this editor, so unaffected; **Lock #2** — the document-validation PATCH (`app/api/sis/students/[enroleeNumber]/document/[slotKey]/route.ts`) 403s the `admissions` role on an **enrolled** student (docs are P-Files') and `p-file` on an **un-enrolled** one (validation is Admissions'); `registrar`/`superadmin` act either side (KD #37). **Amends KD #97:** Records is no longer read-only on the **shared profile** (profile/family become editable from Records via the existing `/profile` + `/family/[parent]` routes) — it stays read-only on the **application-history** axis. Cross-ref Hard Rule #6 (append-only), KD #67/#83 (transfers/movements as historical truth), KD #59/#70 (the two applicationStatus columns + doc-validation queue split), KD #90 (unsynced gap), KD #31/#71 (P-Files enrolled-only). No schema change.

### KD #150

`applicationStatus` is the application **OUTCOME** (append-only); current state lives on `section_students.enrollment_status` (2026-06-26). **Amends KD #147** — narrows its "`applicationStatus` is a current-state mirror kept in sync by the Records→Admissions cascade." **The bug:** the one column carried two meanings — the application's final _outcome_ and the student's _current_ status. They diverge the moment a student **enrols then withdraws**, and the post-enrolment withdrawal route was overwriting `applicationStatus → 'Withdrawn'`, **erasing the fact the application succeeded** (violating KD #147's own "historical truth is append-only" principle) and double-listing the student in **both** the Admissions closed-applications archive **and** Records withdrawn. **The model:** `applicationStatus` = the OUTCOME / furthest-forward status reached (`Enrolled` / `Enrolled (Conditional)`, or a genuine **pre-enrolment** terminal `Cancelled`/`Withdrawn`), **never overwritten by a post-enrolment event**; `section_students.enrollment_status` (`active`/`withdrawn`/`late_enrollee`) is the single source of truth for current state. **Change:** the section-students withdrawal route (`app/api/sections/[id]/students/[enrolmentId]/route.ts`, via extracted pure `buildWithdrawalAdmissionsPatch`) sets only `enrollment_status='withdrawn'` + `withdrawal_date`/`reason` — **no `applicationStatus` write**. Re-enrol still writes a _forward_ `applicationStatus='Enrolled'` (restoring a forward status, not a terminal cascade). **Pre-enrolment terminal flips (stage route, never-enrolled apps) UNCHANGED** — a real outcome. **Consumer rule (audited all 17 terminal readers):** anything detecting _"currently withdrawn"_ must read `section_students.enrollment_status`, NOT `applicationStatus`. Outcome-readers left as-is → the Admissions **closed list + cancellation/terminal counts become cleanly pre-enrolment-only** (more correct). Current-state readers switched: **`lib/supabase/admissions.ts::fetchAdmissionsRoster`** excludes currently-withdrawn via `filterWithdrawnFromRoster` (**critical — without it the bulk "Sync from Admissions" would _reactivate_ a withdrawn student** now that they read `'Enrolled'`); **`lib/sis/process.ts::resolveIsWithdrawn(applicationStatus, ssEnrollmentStatuses)`** is dual-signal + **transfer-aware** (a transfer leaves an old `'withdrawn'` row beside a new `'active'` one — KD #67 — and must NOT read as withdrawn; withdrawn only when no active/late row coexists). **Parent portal (`getAllStudentsByParentEmail`) deliberately UNCHANGED** — decision: **include** withdrawn students (the external `/api/parent/v2/*` surface), since report-card visibility is independently gated by the publication window (KD #10). **Display:** `components/sis/student-status-badges.tsx` — read-only `Application Outcome: {outcome}` + `Current Status: {humanized enrollment_status}`; on the Records student detail (both) + Admissions applicant detail (outcome-only — `enrollment_status` not in scope there). **Seeder:** enrolled-then-withdrawn personas keep `applicationStatus='Enrolled'` (+ `enrollment_status='withdrawn'`); pre-enrolment terminals keep their terminal status (surfaces on a fresh test-AY reseed). **Effect:** an enrolled-then-withdrawn student now appears in Records withdrawn but **not** the Admissions closed list. **No migration, no backfill** (a population check found **0** corrupted rows across AY2025/26/27 — the corruption was latent, prevented go-forward). **Latent/documented:** `lib/sync/students.ts::syncOneStudent`'s `applicationStatus==='Withdrawn'` skip-guard is now incomplete (commented; not hittable today — bulk path protected upstream by `fetchAdmissionsRoster`, direct callers operate only on the unsynced queue). Spec/plan: `docs/superpowers/{specs,plans}/2026-06-26-application-outcome-vs-current-state*`. Cross-ref KD #147 (module ownership), KD #67 (transfers), KD #59/#70 (two `applicationStatus` columns + closed list), KD #10 (publication-window gate), Hard Rule #6 (append-only).

### KD #155

Motivation: `registrar` misdescribed the role — the person holding it (Joann) does school-wide academic-artifact work (grading sheets, attendance workbooks, consolidated forms, report cards), not enrollment/records-office work; `p-file` was internal jargon with no meaning outside this codebase. Also introduces a **display-only** 3-family grouping (not a schema/access concept) for UI presentation: **Academics** (`teacher`, `academic_coordinator`), **Admissions & Enrollment** (`admissions`, `p_file_officer`), **Admin** (`school_admin`, `superadmin`). `academic_coordinator` keeps every access `registrar` had, including the Admissions operational visibility (KD #74) and full Records access, unchanged by its "Academics" family placement. Precedent for the rename mechanics: KD #39 (`admin`→`school_admin`). The SQL helper `is_registrar_or_above()` keeps its exact function name through this rename (only its body's checked string changed) — same reasoning KD #39 used. Historical KD prose elsewhere that already says "registrar"/"p-file" (dozens of entries) is deliberately **not** rewritten — KD #2 above is the sole exception, being the living role-definition index rather than a historical decision narrative. ### KD #159

Nav ↔ `ROUTE_ACCESS` consistency is a **two-directional** invariant, now guarded for every module (2026-07-28; no migration). KD #154 established the no-dead-ends test, but it covered only direction (A) and only the SIS module. A user report ("why can't a school admin view grading sheets?") exposed the _other_ direction, and an exhaustive sweep of all 6 roles × all 7 modules found a second instance plus an unrelated missing guard.

- **Direction A — dead links:** a nav item a role can SEE must not be proxy-blocked. Swept clean; no instances found.
- **Direction B — invisible pages:** a route a role is ALLOWED to open should have some nav path to it. Two real instances, both fixed in `lib/auth/roles.ts`:
  1. **`school_admin` had no Grading group in its Markbook nav at all** — while `teacher`, `academic_coordinator`, and `superadmin` all did. `ROUTE_ACCESS` (`/markbook`), the RLS `is_registrar_or_above()` gate, and the grading page's own role check all allow it (it even grants `canCreate`), and `school_admin` is the **grade-change approver pool** (KD #41), so inspecting a sheet is core to the job. Reachable only by typing the URL.
  2. **`academic_coordinator` → `/sis/admin/staff`** — KD #154 deliberately added her a `ROUTE_ACCESS` row and lists her in the SIS_NAV item's `requiresRoles`, but she never sees the SIS sidebar (the `/sis` catch-all is school_admin+) and no Records cross-link existed — **even though the `SIS_NAV` comment already asserted one did**. Added next to the sibling "Section setup" cross-link.
- **Regression guard** `__tests__/auth/nav-route-consistency-all-modules.test.ts` — both directions × every role, with a `REDIRECT_STUBS` allowlist for the 4 routes that intentionally have no nav entry (`/markbook/masterfile`, `/attendance/calendar`, `/sis/admin/users`, `/admin/admissions` — each a `redirect(...)` one-liner whose `ROUTE_ACCESS` row exists only so the gate fires before the redirect). It must gate on the **module root** first: a role that can't open `/p-files` never sees that sidebar, so naively walking every module's nav for every role produces enormous false-positive noise. **Documented limitation:** direction B checks `ROUTE_ACCESS` **prefixes**, not individual pages, so a page under a broad prefix the role already links elsewhere (exactly case 1 above, `/markbook/grading` under `/markbook`) is NOT covered — page-level coverage was evaluated and rejected as more allowlist-maintenance than signal. That sweep was run once by hand instead.
- **Separate finding from the same sweep — `/markbook/report-cards` had no page-level role guard**, the only Markbook page without one (`insights`, `sections`, `audit-log`, `change-requests`, `grading/new` all have one). Since `ROUTE_ACCESS` gates the broad `/markbook` prefix to teachers too, a teacher reaching the URL rendered the publishing shell. **Not a data leak** — `report_card_publications` is RLS-gated to `is_registrar_or_above()` (migration 007) so the windows came back empty, and every mutation was already `requireRole`-gated — but a broken surface for a role that can't use it, and a defense-in-depth gap if that RLS ever loosened. Guard added matching `/markbook/insights`' role set.
- **Left deliberately unguarded** (checked, judged correct): `/markbook/audit-log` (RLS-gated to `is_registrar_or_above()`, so a teacher sees an empty table) and `/markbook/sections` (`sections` is a reference table readable by all authenticated roles by design — migration 005 calls these "read-only UI scaffolding" — and its `canManage` flag already gates the actions).
