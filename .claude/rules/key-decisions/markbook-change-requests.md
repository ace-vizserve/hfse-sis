## Markbook — change-request workflow

### KD #25

Locked-sheet edits go through `grade_change_requests` workflow (migration 009); server derives `approval_reference`, rejects free-text values.

### KD #88

Grade change-request hardening (migrations 044 + 045). Three correctness + workflow + polish layers on KD #25's flow. **Migration 044**: 10 new nullable columns on `grade_change_requests` — paired primary/secondary review trail (KD #41 dual-reviewer audit) + `eligible_approver_snapshot jsonb` (write-once pool capture) + `notification_status`. Ships `apply_change_request_atomic` SECURITY DEFINER RPC that re-checks `grading_sheets.is_locked FOR UPDATE` and applies the entry patch + flips status to `'applied'` atomically — closes the silent race where a registrar's mid-apply unlock could bypass Hard Rule #5's `approval_reference`. **Migration 045**: `approved_at` (canonical, separate from primary_reviewed_at), `reminder_sent_at` (idempotency for the lazy reminder), `rejection_undone_at` + a partial index for the candidate scan. **Server enforcements**: 422 when applicant has no `studentNumber` at Enrolled-flip; canonical numeric `valuesMatch` (`'85'` matches `85.0`); same-person double-stamp guard + concurrent-approval `.eq('status', 'pending')` optimistic gate; spurious-value 422 (proposed === current); `slot_index` ceiling check against `subject_configs.{ww,pt}_max_slots`; backstop no-op audit row when applying a change-request whose value already matches stored (so the approval_reference trail is never empty). **Workflow**: 2-hour rejection undo via `action: 'undo_rejection'` (rejecting approver only); approved-but-not-applied reminder at 3 days via lazy fire from GET inbox (idempotent stamp-before-send); "Open sheet" CTA on teacher's approved row; aging chip ("approved 5 days ago", muted < 3d / amber 3–7d / destructive > 7d). **Polish**: `lib/env.ts` central env-var module with build-time `console.warn` when `NEXT_PUBLIC_SIS_URL` missing + amber `<SisUrlMissingBanner>` on `/sis/admin/settings`; `MeScopeConfig.enabled?` replaces the sentinel-string pattern in the unified `<DataTable>` shell (KD #84). New AuditActions: `grade_change_undo_rejection` + `reviewer_ordinal` in context. `<EditStageDialog>` surfaces `autoSync.reason` via `toast.warning` when class auto-assign succeeded but section-roster sync skipped.

### KD #123

One-click Approve/Reject from the change-request email — signed action tokens (Sprint 55, 2026-06-05). Extends KD #25/#41/#88. The notification email's Approve/Reject buttons were previously **deep-links** (open `/markbook/change-requests?req=…&action=…`, login required, only auto-open the in-app dialog). They are now **signed, single-effect action links** that decide from the email without a login. **Token** (`lib/change-requests/action-token.ts`, server-only, no DB): a stateless HMAC-SHA256 over `{ requestId, action, approverId }` (base64url payload `.` sig, `timingSafeEqual`), keyed on new server-only env `CHANGE_REQUEST_ACTION_SECRET` (≥32 chars, per-env; rotating invalidates outstanding quick-links; if unset → buttons gracefully degrade to the old deep-links + a build-time warn from `lib/env.ts`). **No time expiry** — validity is "until the request is decided" (single-effect: once it leaves an actionable state the token does nothing). **Flow:** per-approver token in the email → `GET /change-requests/act?token=…` renders a **prefetch-safe confirm page** (`app/(action)/change-requests/act/page.tsx`, unauthenticated — added to `proxy.ts` `PUBLIC_PATHS`; GET never mutates) showing the request + one **Confirm** button (reject requires a reason) → `POST /api/change-requests/act` (token-gated, **no `requireRole`**; resolves the approver via `service.auth.admin.getUserById`) runs the decision **as that approver**. **Key refactor:** the decision pipeline was extracted from the PATCH handler into **`lib/change-requests/decide.ts`** (`decideChangeRequest({ actingUser, action, decisionNote, via })`), shared by the in-app `PATCH /api/change-requests/[id]` (unchanged behavior, still `requireRole`-gated) and the token route — so all guards behave identically (designated-approver check, role gate, status guards, primary-flips-status vs **secondary co-sign** (which works from email too), same-person guard, optimistic `.eq('status', expectedStatus)`, reject-needs-reason, audit, notify). Audit context gains `via: 'in_app' | 'email_token'`. Label/recipient helpers (`fetchLabels`, `fetchRegistrarEmails`, `fetchApproverEmails`) moved to `lib/change-requests/labels.ts` to avoid a `lib`←`app/api` import. All edge cases resolve by re-running `decideChangeRequest` against live state at click time. No migration.

**Update (2026-07-28) — notification emails were silently not sending in prod; root cause was the calling pattern, not Resend.** The 4 places that fire change-request notification emails (`app/api/change-requests/route.ts` ×2, `lib/change-requests/decide.ts`, `app/api/grading-sheets/[id]/entries/[entryId]/route.ts`) wrapped the send in an un-awaited `void (async () => {...})()` after already returning the HTTP response. On Vercel's serverless runtime the execution environment can freeze once the response is sent — nothing guarantees an un-awaited promise finishes. Confirmed in prod: a filed change request's `notification_status` sat at its `'pending'` column default forever (never even reaching the `catch` branch's `'failed'` write), with zero `[notify]`/`[change-requests]` log lines for the request. Fixed by switching all 4 sites to Next.js's `after()` (from `next/server`, stable since Next 15) — registers the callback to run after the response is sent, wired into Vercel's request lifecycle so the function isn't frozen until it resolves. **Test-environment fallout**: `after()` throws "called outside a request scope" when a unit test calls an exported route handler directly (no live Next request context) — fixed once, centrally, via a `next/server` mock in `vitest.setup.ts` (`after: (fn) => { void fn(); }`) rather than per-test-file workarounds.

### KD #156

Cross-module notification bell — surfaces the `changeRequests` realtime signal outside Markbook's own sidebar (2026-07-28). Extends KD #41/#88/#123. The sidebar's `changeRequests` badge (`lib/change-requests/sidebar-counts.ts::getSidebarChangeRequestCount`, live via `lib/sidebar/use-realtime-badges.ts`) was already correct and already live — but only visible on Markbook's own nav item, invisible to an approver browsing any other module. Design/plan: `docs/superpowers/specs/2026-07-28-cross-module-notification-bell-design.md` / `docs/superpowers/plans/2026-07-28-cross-module-notification-bell.md`.

**Placement:** every module already renders a shared, per-module-layout sticky `<header>` bar (`app/(<module>)/layout.tsx` ×7, previously holding only `<SidebarTrigger>`) — **not** part of `<ModuleSidebar>` (KD #58), a distinct architectural element. `<NotificationBell>` (`components/notifications/notification-bell.tsx`) mounts there, right-aligned, next to the collapse toggle, in all 7 layouts. Each layout's `<ModuleSidebar badges={...}>` prop is deliberately **untouched** — the bell's count is its own independent prop, not merged into the sidebar's badge set (avoids a second, redundant realtime subscription inside `<ModuleSidebar>` on the 6 modules whose own nav never shows a `changeRequests` badge).

**Data layer:** `getSidebarChangeRequestPreview(service, role, userId, limit)` — new sibling of `getSidebarChangeRequestCount` in the same file, copying (not re-deriving) its exact per-role/per-current-AY scope so the panel list can never disagree with the badge count (count==drill discipline, KD #124). Backs `GET /api/change-requests/preview` (same role gate as the rest of the change-request flow, capped at 5 rows, labels resolved via the existing `fetchLabels`).

**Live updates:** the `changeRequests`-specific realtime-subscription logic was extracted out of `use-realtime-badges.ts` into a standalone `useChangeRequestCount(role, userId, initial)` hook (`lib/sidebar/use-change-request-count.ts`) — both the sidebar's existing badge and the new bell call it independently (two lightweight per-instance Supabase channels, unique-named via `useId()`, rather than a shared-state provider). `use-realtime-badges.ts` now delegates to it for the `changeRequests` slice; the unrelated `pfileAwaitingVerification` effect is untouched.

**Behavior change to pre-existing, already-shipped code:** `getSidebarChangeRequestCount`'s `superadmin` branch was widened from designated-approver-only (same restriction as `school_admin`) to **unrestricted oversight visibility** (`.eq('status','pending')` only) — matching what the realtime hook had _always_ done for superadmin (an intentional "Oversight scope: full visibility" carve-out with a stale, factually-wrong "matches the page filter" comment) and what the real `/markbook/change-requests` inbox page's `academic_coordinator`-labeled full-visibility branch already implied. This was a genuine **latent pre-existing bug**, not new-code drift: the SSR-rendered badge (restricted) and the live-updated badge (unrestricted) already silently disagreed for superadmin before this feature existed — a superadmin's badge count would visibly jump upward the first time any realtime event fired. Surfaced via the notification bell's stricter "badge must never disagree with panel" requirement exposing the divergence; human decision was to keep the broader oversight visibility and align the restricted functions to it, not the other way around. `getSidebarChangeRequestPreview` widened identically. Only caller outside the 7 layouts, `lib/account/this-term-stats.ts`, is unaffected (gated to `school_admin` only). New `__tests__/change-requests/scope-parity.test.ts` asserts all 3 implementations (`getSidebarChangeRequestCount`, `getSidebarChangeRequestPreview`, the hook's extracted `applyChangeRequestCountScope`) take the same `.or()`-or-not branch per role — closes the gap that let the divergence go undetected by tests.

**Row destination is role-aware:** mirrors the existing sidebar nav's own split (`lib/auth/roles.ts` — teacher's `changeRequests` badge already pointed at `/markbook/grading/requests`, "My Requests"; other gate roles at `/markbook/change-requests`) because the latter redirects non-`school_admin`/`superadmin`/`academic_coordinator` roles away. `teacher` is a bell gate role and does receive rows (their own pending requests) — an unconditional deep-link would have dead-ended them at the module picker.

**Gate roles:** `teacher | academic_coordinator | school_admin | superadmin` only — `admissions`/`p_file_officer` never see the bell (mirrors the pre-existing sidebar-badge gate). On layouts that also allow a non-gate role (SIS, P-Files, Admissions), the count fetch itself is conditional — skipped entirely for the non-gate role, not just hidden client-side.

**Visual:** popover panel (`Popover`/`PopoverContent`, same primitive as `<SidebarProfile>`'s account menu), numeric destructive-pill badge matching the existing sidebar nav-item badge style (not a bare dot), avatar-initials circles per row (student-name-derived, same gradient-circle convention as the sidebar profile pill), `staleTime: 0` on the lazy on-open fetch (closes a window where a 60s-stale cached panel could disagree with the instantly-live badge). Each of the 7 layouts' header `<div className="flex items-center w-full mx-auto max-w-[1440px]">` wrapper co-centers the header row with `PageShell`'s own `max-w-360` (= 1440px) page-content width.

No migration.
